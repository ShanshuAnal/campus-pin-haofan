# docs/AGENTS.md

## 适用范围

本文件适用于文档汇报会话、主控会话、测试会话，以及任何修改 `docs/` 的任务。

文档会话不得修改业务代码，不得创建后端 Controller、Vue 页面、SQL 表结构或工程脚手架。

## 文档类型

`docs/` 目录用于维护：

- 需求文档；
- API 文档；
- 数据库设计说明；
- 测试用例；
- 演示脚本；
- LLM 辅助开发记录；
- PPT 材料；
- 多会话协作流程；
- 任务看板。

## 需求文档

- 需求文档应说明用户角色、核心场景、业务流程和验收标准。
- 需求变更必须说明影响的接口、数据库、前端页面和测试用例。
- 不要把未确认的扩展能力写成 MVP 必做项。

## API 文档

API 文档应包含：

- 接口名称；
- 请求方法；
- 请求路径；
- 权限要求；
- 请求参数；
- 请求示例；
- 响应字段；
- 响应示例；
- 错误码；
- 关联页面或业务流程。

接口文档是前后端并行开发契约。接口变更必须先更新文档，再修改代码。

## 测试用例

测试用例至少覆盖：

- 正常流程；
- 参数为空；
- 金额非法；
- 状态不允许；
- 重复操作；
- 数据不存在；
- 权限不足。

金额分摊、状态流转、付款标记和取餐协同必须有重点测试说明。

## 演示脚本和 PPT 材料

- 演示脚本应围绕 MVP 主流程组织。
- PPT 材料应突出项目定位、技术栈、业务流程、数据库设计、核心实现和测试结果。
- 不要在汇报材料中承诺未实现能力。
- Redis 和 RocketMQ 如未实际接入，只能描述为可选增强或扩展方向。

## LLM 辅助开发记录

开发过程中需要维护 `docs/LLM辅助开发记录.md`，记录：

- 使用阶段；
- 使用工具；
- Prompt 摘要；
- 模型输出内容；
- 人工修改内容；
- 效果评价；
- 模型局限。

记录应客观，不夸大模型能力。

## 文档修改要求

- 文档命名应清晰，避免多个文件表达同一件事。
- 文档中的接口、状态枚举、金额规则必须与代码和 SQL 保持一致。
- 文档会话如果发现业务代码与文档冲突，应记录问题并报告，不要直接修改业务代码。
