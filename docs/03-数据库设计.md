# 数据库设计

## 1. 文档目的

本文档基于 `docs/01-需求说明.md` 和 `docs/02-领域模型与业务规则.md`，设计校园拼好饭系统 MVP 阶段的 MySQL 8 数据库表结构，为后续 `sql/schema.sql`、后端实体、Mapper、DTO/VO、API 文档和测试用例提供依据。

本文档描述数据库设计，并与 `sql/schema.sql`、`sql/data.sql` 保持一致。本次任务只生成 MySQL 初始化脚本，不编写业务代码。

## 2. 设计原则

- MySQL 8 是 MVP 主流程的最终数据源。
- Redis 和 RocketMQ 只作为增强能力，不作为订单、参与者、付款、取餐或通知状态的最终存储。
- 主键统一使用 `bigint`，建议由后端或数据库生成雪花 ID、自增 ID 或其他稳定 ID。
- 金额字段统一使用 `decimal(10,2)`，后端对应 `BigDecimal`。
- 状态字段统一使用 `varchar(32)`，只存稳定英文枚举值，不存中文展示文案。
- 时间字段优先使用 `datetime`。
- 每张业务表必须包含 `create_time`、`update_time`。
- MVP 阶段建议优先使用逻辑外键，由后端保证数据一致性；如后续启用物理外键，需同步评估删除、更新和测试数据维护成本。
- `schema.sql` 不使用物理外键，但建表顺序仍按逻辑依赖从主表到从表排列，并通过字段说明和索引保留逻辑外键关系。
- 用户认证升级为 `accessToken + refreshToken`：注册时写入 `user.account` 和 `user.password_hash`，登录时使用 `username` 映射 `user.account` 并校验密码哈希，登录成功返回双 token；不引入 OAuth2、短信验证码、完整 Spring Security 或复杂 RBAC。
- token 不明文落库，只允许保存 token hash；`user_refresh_token.token_hash` 保存 refreshToken hash。

## 5. 表设计明细

### 5.1 `user`

用途：存储系统中的学生用户基础信息，用于登录识别、发起拼单、加入拼单、标记付款和被指定为取餐人。

主键：`id`

核心字段：

| 字段名 | 类型 | 约束建议 | 说明 |
| --- | --- | --- | --- |
| `id` | `bigint` | PK | 用户 ID |
| `account` | `varchar(64)` | NOT NULL, UNIQUE | 登录账号或学号类唯一标识 |
| `password_hash` | `varchar(255)` | NOT NULL | 加密后的密码哈希，不存明文密码 |
| `nickname` | `varchar(64)` | NOT NULL | 昵称或姓名 |
| `phone` | `varchar(32)` | NULL | 联系方式，MVP 可选 |
| `status` | `varchar(32)` | NOT NULL | 用户状态，如 `ACTIVE`、`DISABLED` |
| `last_login_time` | `datetime` | NULL | 最近登录时间 |
| `last_login_ip` | `varchar(64)` | NULL | 最近登录 IP |
| `password_update_time` | `datetime` | NULL | 最近一次密码更新时间 |
| `create_time` | `datetime` | NOT NULL | 创建时间 |
| `update_time` | `datetime` | NOT NULL | 更新时间 |

外键逻辑：

- `group_order.creator_id` 逻辑关联 `user.id`。
- `group_order.pickup_user_id` 逻辑关联 `user.id`。
- `order_participant.user_id` 逻辑关联 `user.id`。
- `payment_record.user_id`、`payment_record.confirm_user_id` 逻辑关联 `user.id`。
- `pickup_record.pickup_user_id` 逻辑关联 `user.id`。
- `order_status_log.operator_id` 逻辑关联 `user.id`。
- `notification_record.receiver_id` 逻辑关联 `user.id`。

索引建议：

| 索引 | 字段 | 场景 |
| --- | --- | --- |
| `uk_user_account` | `account` | 登录账号唯一性校验 |
| `idx_user_status` | `status` | 管理或筛选可用用户，MVP 可按实际查询决定是否创建 |

认证字段说明：

- API 字段 `username` 映射数据库字段 `user.account`。
- `password_hash` 仅保存后端加密后的密码哈希值，不保存明文密码。
- 注册接口 `POST /api/auth/register` 写入用户时，必须由后端完成密码加密，再落库到 `password_hash`。
- 登录接口 `POST /api/auth/login` 使用 `username` 查询 `user.account`，再校验提交密码与 `password_hash` 是否匹配。
- 登录成功返回 `accessToken`、`refreshToken`、`expiresIn` 和用户信息。
- 当前用户接口 `GET /api/auth/me` 根据 accessToken 解析出的用户 ID 查询 `user` 表，不返回 `password_hash`。
- 刷新接口 `POST /api/auth/refresh` 使用 refreshToken 换取新的 accessToken 和 refreshToken。
- 登出接口 `POST /api/auth/logout` 将 refreshToken 作废。
- `refreshToken` 不得明文落库，只允许保存 hash 到 `user_refresh_token.token_hash`。
- 演示数据中的 `password_hash` 使用占位哈希值，仅用于初始化数据结构和联调，不代表真实生产密码策略。
- 实际本地测试建议优先通过注册接口创建用户，避免演示占位哈希与后端密码算法不匹配。

### 5.2 `user_refresh_token`

用途：存储用户 refreshToken 会话、refreshToken hash、过期时间和作废状态。该表用于支持 accessToken + refreshToken 认证升级。refreshToken 不明文落库，只保存 hash。

主键：`id`

核心字段：

| 字段名 | 类型 | 约束建议 | 说明 |
| --- | --- | --- | --- |
| `id` | `bigint` | PK | token 会话 ID |
| `user_id` | `bigint` | NOT NULL | 用户 ID，逻辑关联 `user.id` |
| `token_hash` | `varchar(255)` | NOT NULL, UNIQUE | refreshToken 哈希值，不保存明文 refreshToken |
| `expire_time` | `datetime` | NOT NULL | refreshToken 过期时间 |
| `revoked` | `tinyint` | NOT NULL, DEFAULT 0 | 作废标记，`0` 表示有效，`1` 表示已作废 |
| `revoked_time` | `datetime` | NULL | 作废时间 |
| `create_time` | `datetime` | NOT NULL | 创建时间 |
| `update_time` | `datetime` | NOT NULL | 更新时间 |

索引建议：

| 索引 | 字段 | 场景 |
| --- | --- | --- |
| `uk_user_refresh_token_hash` | `token_hash` | refreshToken hash 唯一校验和刷新查询 |
| `idx_user_refresh_token_user_revoked` | `user_id`, `revoked` | 查询用户有效或已作废 token 会话 |
| `idx_user_refresh_token_expire_revoked` | `expire_time`, `revoked` | 清理过期 refreshToken 或查询有效 token |

认证持久化规则：

- 后端收到明文 token 后先计算 hash，再查询或写入数据库。
- 数据库不得保存 refreshToken 明文。
- 登录成功时创建一条 `revoked = 0` 的 token 会话记录。
- refresh 成功时建议轮换 refreshToken：旧记录设置为 `revoked = 1` 并写入 `revoked_time`，新建一条 `revoked = 0` 记录。
- logout 时将对应 refreshToken 记录设置为 `revoked = 1` 并写入 `revoked_time`。
- 后端校验 refreshToken 时必须同时校验 `token_hash`、`expire_time` 和 `revoked`。

### 5.4 `order_participant`

- `payment_record.participant_id` 逻辑关联 `order_participant.id`。

唯一约束：

| 索引 | 字段 | 场景 |

索引建议：

| 索引 | 字段 | 场景 |

| `idx_order_participant_payment` | `group_order_id`, `payment_status` | 统计拼单付款进度 |

#### `group_order` 与 `order_participant` 的关系

- `group_order` 是拼单主表，一条记录表示一次拼单。
- `order_participant` 是拼单参与表，一条记录表示一个用户在某个拼单中的参与身份。
- 两者是 `1:N` 关系：一个拼单可以有多个参与者，一个参与记录只属于一个拼单。
- 用户和拼单之间是 `N:N` 关系，通过 `order_participant` 拆解；唯一索引 `group_order_id + user_id` 保证同一用户不能重复加入同一拼单。
- 拼单发起人也可以作为参与者加入自己的拼单。此时 `group_order.creator_id` 表示管理权限身份，`order_participant.user_id` 表示点餐和付款身份，两者不能混淆。

#### 金额分摊字段落库方式

锁单时后端执行金额计算，并将结果同时落库到订单级和成员级字段：

订单级字段存储在 `group_order`：

- `original_total_amount`：所有 `order_participant.original_amount` 之和。
- `actual_discount_amount`：满足满减后实际生效的优惠金额，未满足时为 `0.00`。
- `payable_total_amount`：订单原始总金额减实际优惠金额。
- `rounding_adjustment_amount`：分摊尾差总调整额，用于解释成员应付金额汇总与比例计算的差异。

成员级字段存储在 `order_participant`：

- `original_amount`：成员餐品原始金额，可由 `meal_item.subtotal_amount` 汇总得到。
- `discount_share_amount`：按成员原始金额占比分摊到的优惠金额。
- `payable_amount`：成员最终应付金额。
- `rounding_adjustment_amount`：成员承担或补齐的尾差金额。

一致性要求：

```text
sum(order_participant.original_amount) = group_order.original_total_amount
sum(order_participant.discount_share_amount) = group_order.actual_discount_amount
sum(order_participant.payable_amount) = group_order.payable_total_amount
```

尾差处理策略固定为由拼单发起人承担或补齐。若发起人也是参与者，则将尾差记录到该发起人的 `order_participant.rounding_adjustment_amount`；若发起人未参与点餐，则后端应阻止锁单或要求发起人先加入拼单，避免尾差无处落库。

配送费和包装费 MVP 阶段不单独建字段。处理策略如下：

- 如果费用明确归属于某个成员的餐品，则并入该成员的 `meal_item.subtotal_amount` 和 `order_participant.original_amount`。
- 如果费用需要全员分摊，则由发起人在线下或前端表单中手动拆分后计入各成员原始金额。
- 数据库只保存最终进入分摊计算的成员原始金额，不单独保存 `delivery_fee`、`package_fee` 等字段。
- 后续增强如需自动按人数、餐品或比例拆分配送费和包装费，应先更新本文档和 `schema.sql`，再修改后端金额计算逻辑。

### 5.6 `payment_record`

用途：存储付款标记和确认过程，用于保留付款行为记录。当前付款状态以 `order_participant.payment_status` 为查询主字段，`payment_record` 用于过程追踪。

核心字段：

| 字段名 | 类型 | 约束建议 | 说明 |

## 7. 数据一致性要求

- 加入拼单时必须校验 `group_order.status = CREATED`、截止时间未过、人数未满。
- 创建拼单时必须填写 `group_order.pickup_location`，用于明确约定取餐地点。
- 加入成功后创建 `order_participant` 和至少一条 `meal_item`，并更新 `group_order.participant_count`、`group_order.original_total_amount`。
- 锁单时必须重新从 `order_participant` 或 `meal_item` 汇总金额，避免依赖前端提交的汇总值。
- 锁单成功后写入最终金额分摊字段，后续付款、展示和统计以落库结果为准。
- 付款当前状态保存在 `order_participant.payment_status`，付款过程记录追加到 `payment_record`。
- 取餐当前状态保存在 `pickup_record.pickup_status`，关键状态变化追加到 `order_status_log`。
- 拼单、付款、取餐状态变更必须由后端校验合法流转，数据库不直接承担状态机校验。
