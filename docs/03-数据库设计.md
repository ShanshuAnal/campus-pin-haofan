# 校园拼好饭系统 V2 数据库设计

## 1. 文档定位

本文描述校园拼好饭系统 V2 的数据库设计口径。

当前仓库中 `sql/schema.sql` 仍是数据库结构唯一来源。本次 SQL 会话已将 V2 取消、超时、事件记录和必要索引同步到 `sql/schema.sql` 与 `sql/data.sql`。

## 2. 数据库原则

- MySQL 8 是核心数据源。
- `sql/schema.sql` 是数据库结构唯一来源。
- 金额字段统一使用 `decimal(10,2)`。
- 状态字段统一使用 `varchar(32)`。
- 每张业务表必须包含 `create_time`、`update_time`。
- 当前 schema 仍不使用物理外键，依靠 ID 字段、唯一约束、索引和后端事务校验维护逻辑外键关系。
- 涉及状态推进、金额计算、成员加入、取消和超时关闭的操作必须使用事务。
- Redis 和 RocketMQ 不作为核心状态源。
- V2 引入的事件表用于记录延迟、异常、取消和超时，不把延迟强行设计成主状态。

| `group_order` | 拼单主表 | 已补充 V2 取消、超时、版本和事件时间字段 |

| `notification_record` | 通知记录 | 保留，仍是增强表 |
| `group_order_event` | 拼单事件记录 | V2 新增，记录取消、超时、延迟和异常事件 |

## 4. V2 逻辑模型

```text
user
  ├─ group_order.creator_id
  ├─ group_order.pickup_user_id
  ├─ order_participant.user_id
  ├─ payment_record.user_id
  ├─ pickup_record.pickup_user_id
  └─ group_order_event.operator_id

group_order
  ├─ order_participant
  │    └─ meal_item
  ├─ payment_record
  ├─ pickup_record
  ├─ order_status_log
  ├─ group_order_event
  └─ notification_record
```

## 5. 表设计口径

### 5.1 user

用途：存储用户账号、昵称、联系方式和认证状态。

关键字段口径：

| 字段 | 说明 |
| --- | --- |
| `id` | 用户 ID |
| `account` | 数据库登录账号字段 |
| `password_hash` | 加密密码摘要 |
| `nickname` | 昵称 |
| `phone` | 手机号，可选 |
| `avatar_url` | 头像地址，可选 |
| `status` | 用户状态 |
| `last_login_time` | 最近登录时间 |
| `create_time` | 创建时间 |
| `update_time` | 更新时间 |

API 对外字段名统一使用 `username`，映射数据库字段 `user.account`。

### 5.2 user_refresh_token

用途：保存 refreshToken 摘要，支持登录续期与登出作废。

规则：

- token 不明文落库；
- 只保存 SHA-256 摘要；
- accessToken 黑名单存储在 Redis；
- Redis key 为 `auth:blacklist:access:{tokenHash}`；
- TTL 为 accessToken 剩余有效期。

### 5.3 group_order

用途：拼单主表，承载拼单生命周期、金额汇总和取餐约定。

当前字段需要覆盖：

| 字段 | 说明 |
| --- | --- |
| `id` | 拼单 ID |
| `creator_id` | 发起人 ID |
| `title` | 拼单标题 |
| `order_type` | 拼单类型 |
| `merchant_name` | 商家或窗口名称 |
| `pickup_location` | 约定取餐地点 |
| `deadline_time` | 拼单截止时间 |
| `max_participants` | 最大参与人数 |
| `participant_count` | 当前参与人数 |
| `discount_threshold_amount` | 凑单或满减门槛 |
| `discount_amount` | 配置优惠金额 |
| `original_total_amount` | 原始总金额 |
| `actual_discount_amount` | 实际生效优惠金额 |
| `payable_total_amount` | 最终应付总金额 |
| `rounding_adjustment_amount` | 尾差调整金额 |
| `status` | 拼单主状态 |
| `pickup_user_id` | 取餐人 ID |
| `remark` | 备注 |
| `locked_time` | 锁单时间 |
| `finish_time` | 完成时间 |
| `cancel_time` | 取消时间 |
| `create_time` | 创建时间 |
| `update_time` | 更新时间 |

V2 已新增或强化字段：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `cancel_user_id` | `bigint` | 取消操作人，通常为发起人 |
| `cancel_reason` | `varchar(255)` | 取消原因 |
| `cancel_time` | `datetime` | 取消时间 |
| `expired_time` | `datetime` | 系统超时关闭时间 |
| `expire_reason` | `varchar(255)` | 超时关闭原因 |
| `version` | `int` | 乐观锁版本号 |
| `last_event_time` | `datetime` | 最近事件时间，便于列表展示 |

状态值：

```text
CREATED, LOCKED, ORDERED, DELIVERING, ARRIVED, PICKED_UP,
FINISHED, CANCELLED, EXPIRED
```

`CANCELLED` 与 `EXPIRED` 的区别：

- `CANCELLED`：人为主动取消，通常由发起人触发，必须记录 `cancel_user_id`、`cancel_reason`、`cancel_time`。
- `EXPIRED`：系统根据 `deadline_time` 判断超时自动关闭，通常无人工操作人，必须记录 `expired_time`、`expire_reason`。
- 两者都是终态。进入终态后禁止继续加入、锁单、付款标记和取餐推进。

### 5.4 order_participant

用途：记录用户参与拼单及金额分摊结果。

关键字段口径：

| 字段 | 说明 |
| --- | --- |
| `id` | 参与记录 ID |
| `group_order_id` | 拼单 ID |
| `user_id` | 成员用户 ID |
| `original_amount` | 原始金额 |
| `discount_share_amount` | 分摊优惠 |
| `payable_amount` | 应付金额 |
| `payment_status` | 付款状态 |
| `remark` | 备注 |
| `create_time` | 创建时间 |
| `update_time` | 更新时间 |

约束：

- `group_order_id + user_id` 必须唯一；
- 金额字段统一 `decimal(10,2)`；
- 付款状态统一 `varchar(32)`。

V2 当前不改变该表结构。拼单成员并发冲突优先由 `group_order.version` 和后端事务控制。

### 5.5 meal_item

用途：记录成员餐品明细。

关键字段口径：

| 字段 | 说明 |
| --- | --- |
| `id` | 餐品条目 ID |
| `participant_id` | 参与记录 ID |
| `item_name` | 餐品名称 |
| `unit_price` | 单价 |
| `quantity` | 数量 |
| `subtotal_amount` | 小计 |
| `create_time` | 创建时间 |
| `update_time` | 更新时间 |

规则：

- `subtotal_amount = unit_price * quantity`；
- 所有金额字段必须由后端使用 `BigDecimal` 计算并校验。

### 5.6 payment_record

用途：记录成员付款标记和发起人确认付款。

关键字段口径：

| 字段 | 说明 |
| --- | --- |
| `id` | 付款记录 ID |
| `group_order_id` | 拼单 ID |
| `participant_id` | 参与记录 ID |
| `user_id` | 付款成员 ID |
| `amount` | 付款金额 |
| `payment_status` | 付款状态 |
| `operator_id` | 操作人 ID |
| `remark` | 备注 |
| `create_time` | 创建时间 |
| `update_time` | 更新时间 |

V2 中付款争议不新增付款主状态，优先写入 `group_order_event`。

### 5.7 pickup_record

用途：记录取餐协同状态。

关键字段口径：

| 字段 | 说明 |
| --- | --- |
| `id` | 取餐记录 ID |
| `group_order_id` | 拼单 ID |
| `pickup_user_id` | 取餐人 ID |
| `pickup_location` | 实际取餐地点或履约阶段地点 |
| `pickup_status` | 取餐状态 |
| `remark` | 备注 |
| `create_time` | 创建时间 |
| `update_time` | 更新时间 |

V2 当前不改变该表结构。取餐状态推进仍通过后端事务校验当前 `pickup_status` 和 `group_order.status`。

取餐状态：

```text
WAITING_ORDER, WAITING_DELIVERY, ARRIVED, PICKED_UP, DISTRIBUTED
```

当 `pickup_status = DISTRIBUTED` 时，`group_order.status` 同步为 `FINISHED`。

### 5.8 order_status_log

用途：记录主状态变更历史。

规则：

- 主状态变化必须写日志；
- 日志只追加，不修改历史；
- 日志可与 `group_order_event` 并存。

### 5.9 notification_record

用途：记录异步通知发送结果。

V2 口径：

- 仍是增强表；
- MVP 主流程不依赖通知成功；
- RocketMQ 通知消费失败不改变拼单状态。

### 5.10 group_order_event

V2 新增表，用于记录取消、超时、延迟、异常和备注。该表承担订单事件日志职责；主状态变化仍写入 `order_status_log`，延迟、缺餐、联系失败、付款争议等不强行改变主状态的内容写入 `group_order_event`。

字段：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | `bigint` | 事件 ID |
| `group_order_id` | `bigint` | 拼单 ID |
| `event_type` | `varchar(32)` | 事件类型 |
| `event_level` | `varchar(32)` | `INFO`、`WARN`、`ERROR` |
| `operator_id` | `bigint` | 操作人 ID，系统事件可为空 |
| `operator_role` | `varchar(32)` | `CREATOR`、`PICKUP_USER`、`PARTICIPANT`、`SYSTEM` |
| `title` | `varchar(100)` | 事件标题 |
| `content` | `varchar(500)` | 事件内容 |
| `before_status` | `varchar(32)` | 事件前拼单主状态 |
| `after_status` | `varchar(32)` | 事件后拼单主状态 |
| `event_time` | `datetime` | 事件发生时间 |
| `create_time` | `datetime` | 创建时间 |
| `update_time` | `datetime` | 更新时间 |

建议索引：

- `idx_event_order_time(group_order_id, event_time)`；
- `idx_event_type_time(event_type, event_time)`；
- `idx_event_operator(operator_id, event_time)`。

### 5.11 async_message_record

该表不是必做，只有当后端需要更强的消息可追踪能力时再新增。

建议字段：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | `bigint` | 记录 ID |
| `message_key` | `varchar(128)` | 消息业务键 |
| `topic` | `varchar(128)` | MQ topic |
| `message_type` | `varchar(64)` | 消息类型 |
| `biz_id` | `bigint` | 业务 ID |
| `status` | `varchar(32)` | 处理状态 |
| `retry_count` | `int` | 重试次数 |
| `last_error` | `varchar(500)` | 最近错误 |
| `create_time` | `datetime` | 创建时间 |
| `update_time` | `datetime` | 更新时间 |

## 6. 索引设计建议

### 6.1 group_order

建议索引：

- `idx_group_order_status_deadline(status, deadline_time)`：按状态筛选并辅助超时检查；
- `idx_group_order_deadline_status(deadline_time, status)`：按截止时间扫描待过期拼单；

- `idx_group_order_pickup_user(pickup_user_id, status)`：我负责取餐；

- `idx_group_order_status_last_event(status, last_event_time)`：按事件活跃度展示。

### 6.2 order_participant

建议索引和约束：

- `uk_participant_order_user(group_order_id, user_id)`：防止重复加入；

- `idx_participant_payment(payment_status)`：待付款筛选。

### 6.3 payment_record

建议索引：

- `idx_payment_order(group_order_id, create_time)`；
- `idx_payment_user(user_id, create_time)`；

### 6.4 pickup_record

建议索引：

## 7. Redis 数据设计

Redis 是增强能力，其中 accessToken 黑名单为认证方案必选存储。

| 场景 | Key | TTL |
| --- | --- | --- |
| accessToken 黑名单 | `auth:blacklist:access:{tokenHash}` | accessToken 剩余有效期 |
| 防重复提交 | `idem:{userId}:{method}:{path}:{bizKey}` | 30 秒到 5 分钟 |
| 拼单短时锁 | `lock:group-order:{orderId}` | 5 到 15 秒 |
| 拼单大厅缓存 | `cache:group-order:hall:{filtersHash}` | 30 到 60 秒 |
| 拼单详情缓存 | `cache:group-order:detail:{orderId}` | 30 到 60 秒 |

规则：

- Redis 锁失败不能直接判定业务失败，最终以 MySQL 状态校验为准；
- 缓存命中只用于读性能优化；
- 写操作成功后应删除或延迟失效相关缓存；
- token 和业务敏感值不明文存储。

## 8. RocketMQ 数据边界

RocketMQ 可用于：

- 超时检查消息；
- 异步通知消息；
- 统计聚合消息；
- 延迟提醒消息。

消息处理规则：

- 消费者必须重新读取 MySQL；
- 状态更新必须通过数据库事务完成；
- 消息重复消费必须幂等；
- 必要时使用 `async_message_record` 记录消费状态；
- MQ 不作为最终状态来源。

## 10. 迁移与重建建议

本次任务已修改 `sql/schema.sql` 和 `sql/data.sql`。由于当前脚本包含 `DROP TABLE IF EXISTS`，开发环境建议直接重建数据库后重新执行初始化脚本。

如果本地数据库已经按 MVP schema 初始化：

- 开发环境建议重建数据库；
- 如需保留现有业务数据，应另行提供 `ALTER TABLE` 与数据回填迁移脚本，不直接运行带 `DROP TABLE` 的初始化脚本；
- 后端实体、Mapper、DTO、VO、API 文档和测试用例必须同步 V2 新字段与 `group_order_event` 表；
- 任何后续 SQL 变更都必须同步本文。
