# LLM 辅助开发总结

## 1. 使用方式概述

本项目采用多会话 LLM 协作开发方式。不同会话分别承担主控、后端、前端、SQL、测试和文档汇报职责，并通过 `AGENTS.md`、`docs/CODEX_WORKFLOW.md` 和 `docs/TASK_BOARD.md` 约束修改范围和交接格式。

LLM 不是直接替代开发者完成项目，而是作为需求分析、设计草稿、代码生成、测试补充和冲突排查的协作工具。关键业务边界、状态口径、接口契约、数据库变更和最终验收仍由人工判断。

## 2. 多会话分工

| 会话 | 主要职责 | 典型产出 |
| --- | --- | --- |
| 主控会话 | 需求澄清、领域建模、接口/数据库契约、任务拆分、冲突收口 | 需求文档、领域规则、API 文档、V2 设计、任务看板 |
| 后端会话 | Spring Boot 工程、业务接口、金额计算、状态流转、后端测试 | Controller、Service、Mapper、DTO/VO、单元测试 |
| 前端会话 | Vue 页面、API 封装、状态管理、联调体验 | 拼单大厅、详情页、我的拼单、数据看板 |
| SQL 会话 | schema、data、数据库设计同步 | `schema.sql`、`data.sql`、数据库设计文档 |
| 测试会话 | 测试用例、接口验证、Bug 复现、回归检查 | 测试矩阵、Service 测试、集成测试、缺陷记录 |
| 文档汇报会话 | 演示脚本、PPT 大纲、LLM 记录、汇报材料 | 演示脚本、项目总结、PPT 大纲 |

## 3. AGENTS.md 的约束作用

`AGENTS.md` 在项目中起到“开发宪法”的作用：

- 明确项目定位：校园拼单协同系统，不是外卖平台；
- 限定技术栈：后端 Java 21 + Spring Boot 3.2.x + MyBatis-Plus + MySQL 8，前端 Vue3 + Vite + TypeScript；
- 限制文件边界：后端会话不随意改前端，文档会话不写业务代码；
- 强制接口和数据库变更先更新文档；
- 要求每次任务结束说明修改文件、验证方式和影响范围；
- 要求维护 `docs/TASK_BOARD.md`，便于多会话协作。

这些规则降低了多会话并行时互相覆盖、接口漂移和数据库不同步的风险。

## 4. LLM 主要帮助了什么

### 4.1 需求分析

LLM 辅助把模糊的“拼好饭”想法拆成项目背景、用户角色、核心流程、MVP 范围、V2 范围和暂不实现功能。人工在此基础上明确系统不接真实商家、不接真实支付、不做即时聊天，避免项目膨胀成外卖平台。

### 4.2 领域模型和状态流转

LLM 帮助整理了拼单、参与者、餐品、付款记录、取餐记录、状态日志和履约事件等对象。状态设计中多次通过主控会话收口：

- `CANCELLED` 表示发起人主动取消；
- `EXPIRED` 表示系统超时关闭；
- 延迟、缺餐、联系失败、支付争议不进入主状态，而是记录到事件时间线；
- 金额计算统一使用 `BigDecimal`；
- 终态后禁止继续加入、锁单、模拟支付和取餐推进。

### 4.3 API、数据库和认证冲突收口

开发过程中出现过多次契约不一致，LLM 辅助主控会话整理问题、生成修订方案并同步任务看板。

典型冲突包括：

- API 路径曾出现 `/api/orders` 和 `/api/group-orders` 两种口径，最终统一为拼单资源使用 `/api/group-orders`；
- API 字段 `username` 与数据库字段 `user.account` 需要映射；
- 发起拼单缺少 `pickup_location`，后续补齐约定取餐地点字段；
- MVP 阶段 `EXPIRED` 是否实现存在分歧，先延后，V2 再作为超时关闭状态重新引入；
- 认证从轻量 token 升级为 accessToken + refreshToken，refreshToken 只存 SHA-256 摘要；
- accessToken 黑名单最初有内存降级口径，后续人工收口为 Redis 必选；
- 付款状态从 `PAID/CONFIRMED` 调整为模拟托管资金流，明确不处理真实资金。

### 4.4 后端实现

LLM 在后端会话中主要提升了以下效率：

- 快速生成 Spring Boot 工程结构、Entity、Mapper、DTO、VO 和枚举；
- 根据 API 文档生成 Controller 和 Service 骨架；
- 补齐金额分摊、状态校验、权限校验、重复操作拒绝等分支；
- 根据测试反馈定位并修复排序、状态口径、Redis 黑名单等问题；
- 生成单元测试和集成测试骨架。

人工重点审查业务规则是否正确，例如锁单后能否修改、谁承担尾差、取餐人是否必须是参与者、终态是否允许操作、Redis 不可用时能否降级等。

### 4.5 前端实现

LLM 辅助前端从初始页面和 mock 数据逐步迁移到真实接口：

- 搭建 Vue3 + Vite + TypeScript + Element Plus 工程；
- 生成登录、拼单大厅、发起拼单、详情页、我的拼单、数据看板等页面；
- 封装 Axios、Pinia store 和 token 管理；
- 将大厅从表格式后台页面改为卡片化产品首页；
- 将详情页改为围绕发起、加入、锁单、模拟支付、取餐、事件的流程式页面；
- 补充终态禁用、权限错误、事件时间线和模拟资金流文案。

人工重点审查页面是否符合“校园拼单产品”定位，而不是变成管理后台。

### 4.6 测试和验收

LLM 辅助测试会话从文档和代码中提炼测试矩阵，覆盖认证、拼单、锁单、金额、付款、取餐、取消、超时、事件、Redis 幂等和短时锁。测试会话还发现并推动修复了 API 路径、EXPIRED 口径、付款接口缺口和完成拼单接口差异等问题。

## 5. 模型擅长的地方

- 快速把自然语言需求转成结构化文档；
- 根据已有代码模式生成相似模块；
- 枚举状态机的正常路径和异常路径；
- 对比文档、SQL、代码和测试，发现字段或路径不一致；
- 快速补齐测试用例、边界条件和交接说明；
- 维护多文件之间的术语一致性。

## 6. 模型暴露的问题

- 容易沿用旧上下文中的接口路径或状态名称；
- 容易把“增强能力”写得像“已实现主流程”；
- 容易在没有证据时把部署、联调或性能结果写得过满；
- 对支付、认证、并发等高风险模块需要人工强约束；
- 多会话并行时，如果没有任务看板和文件边界，容易覆盖其他会话改动；
- 对 UI 体验的初稿可用，但仍需要人工判断是否符合产品定位。

## 7. 人工介入的关键决策

| 决策 | 人工判断 |
| --- | --- |
| 项目边界 | 不做外卖平台，不接真实商家和真实支付 |
| 认证方案 | 不引入完整 Spring Security、OAuth2、短信验证码或复杂 RBAC |
| 资金流 | 模拟支付只做状态流转，不处理真实资金 |
| 状态模型 | 控制主状态数量，延迟和异常进入事件时间线 |
| 并发控制 | MySQL 事务和状态校验为主，Redis 只辅助 |
| RocketMQ | 只做超时检查和异步增强，不作为状态源 |
| 文档优先 | 接口和数据库变更先改文档，再改代码 |
| 汇报材料 | 已实现和可扩展能力分开写，不编造部署截图 |

## 8. 使用 LLM 开发项目的经验

1. 先写规则，再让模型写代码。  
   `AGENTS.md` 和领域文档能显著减少模型自由发挥。

2. 主控会话必须存在。  
   多会话并行时，必须有人负责统一需求、接口、数据库和任务顺序。

3. 文档不是形式，是契约。  
   API 文档和 schema 是前后端、测试和 SQL 会话协作的共同依据。

4. 测试会话要独立。  
   让测试会话从代码外部审查，可以发现模型和实现会话忽略的契约问题。

5. 中间件要守边界。  
   Redis 和 RocketMQ 可以提升体验和可靠性，但不能替代 MySQL 状态校验。

6. 汇报材料要克制。  
   LLM 很擅长写漂亮总结，但课程汇报必须区分已实现、已设计、待验证和可扩展。

## 9. 对项目质量的影响

LLM 提升了项目推进速度，尤其是在文档生成、代码骨架、接口封装和测试矩阵方面。但项目最终质量主要来自三件事：

- 人工持续收口业务边界；
- 多会话严格遵守文件和职责边界；
- 自动化测试和联调验证不断回推文档与实现一致。

因此，本项目更适合作为“LLM 辅助软件工程流程”的案例，而不是“让模型一次性生成完整系统”的案例。
