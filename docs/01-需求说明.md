# 校园拼好饭系统 V2 需求说明

## 1. 项目定位

校园拼好饭系统是面向高校学生的校园拼单协同产品，服务外卖、食堂、奶茶、夜宵等校园高频拼单场景。

系统不是外卖平台，不接入真实商家接口，不接入真实支付接口，不做即时聊天。V2 的重点是把“群聊里临时凑单”的过程产品化：让学生能快速发现拼单、判断是否值得加入、清楚知道自己该付多少钱、谁负责取餐、当前是否延迟或异常，以及拼单最终如何结束。

## 2. 背景问题

当前校园拼单通常依赖群聊或口头沟通，存在以下问题：

- 拼单信息散落在聊天记录里，新成员难以理解规则、截止时间和取餐地点；
- 满减进度、优惠分摊和尾差需要人工算，容易出错；
- 付款只是口头确认，成员是否已付、发起人是否确认不透明；
- 取餐状态、延迟、缺餐、联系不上等异常缺少统一记录；
- 拼单取消和超时关闭口径不清，容易出现成员继续加入或付款；
- 前端如果做成管理后台，学生使用时缺少“校园拼单产品”的效率和代入感。

V2 不是推翻 MVP，而是在当前已完成的登录、拼单、金额分摊、付款标记、取餐协同、我的拼单、数据看板基础上，补齐取消、超时、异常事件、并发控制和产品化体验。

## 3. V2 目标

V2 目标分为业务闭环、工程可靠性和产品体验三类。

| 目标 | 说明 |
| --- | --- |
| 业务闭环完整 | 覆盖发起、加入、锁单、付款、取餐、完成、取消、超时关闭和异常记录 |
| 状态模型克制 | 允许新增 `EXPIRED`，但不因延迟、缺餐、催付等扩散主状态 |
| 权限清晰 | 取消、超时、延迟、付款、取餐均有明确操作人和拒绝规则 |
| 数据一致 | MySQL 事务和状态校验作为并发控制主手段，Redis 只辅助 |
| 异步增强 | RocketMQ 只用于通知、超时检查、统计聚合，不作为状态最终来源 |
| 前端产品化 | 从后台式表格改为校园拼单产品体验，重点重做拼单大厅和详情页 |

## 4. 用户角色

| 角色 | 说明 | 核心权限 |
| --- | --- | --- |
| 普通学生 | 浏览和加入拼单的主要用户 | 浏览大厅、加入拼单、查看详情、标记本人付款、查看取餐状态 |
| 拼单发起人 | 创建拼单并负责推进协同流程 | 锁单、取消可取消拼单、确认付款、指定取餐人、记录异常、推进取餐 |
| 取餐人 | 由发起人指定，负责履约同步 | 更新取餐状态、记录取餐相关异常和延迟 |
| 系统任务 | 后端定时任务或 RocketMQ 消费者 | 执行超时检查、异步通知、统计聚合 |
| 管理员 | V2 非重点角色 | 查看异常数据、辅助演示或测试，不进入学生主流程 |

## 5. 当前 MVP 已完成能力

V2 必须保留并兼容当前 MVP 能力：

- 注册、登录、获取当前用户、刷新 token、登出；
- 拼单大厅查询与发起拼单；
- 加入拼单与餐品明细；
- 拼单详情；
- 锁单和优惠分摊；
- 成员标记付款、发起人确认付款；
- 指定取餐人、更新取餐状态；
- `pickupStatus = DISTRIBUTED` 后同步拼单 `FINISHED`；
- 我的拼单，包含我发起、我参与、我取餐、待付款、历史；
- 数据看板基础统计；
- Redis accessToken 黑名单；
- MySQL + Redis 后端集成测试已覆盖主流程。

## 6. V2 主流程

```text
登录
-> 浏览拼单大厅
-> 发起或加入拼单
-> 查看满减进度和成员清单
-> 锁定拼单
-> 生成优惠分摊
-> 成员标记付款
-> 发起人确认付款
-> 指定取餐人
-> 更新取餐状态
-> 必要时记录延迟或异常事件
-> 分发完成
-> 拼单完成
```

并行闭环：

```text
CREATED 未锁单 -> 发起人取消 -> CANCELLED
CREATED 超过截止时间且未锁单 -> 系统超时关闭 -> EXPIRED
LOCKED/ORDERED 后发生无法继续 -> 发起人取消并记录原因 -> CANCELLED
履约延迟或异常 -> 记录事件，不改变主状态
```

## 7. V2 必做范围

| 能力 | 说明 |
| --- | --- |
| 取消拼单 | 发起人可在规则允许范围内取消拼单，必须填写原因，已付款成员需提示线下处理 |
| 超时自动关闭 | `CREATED` 且超过 `deadlineTime` 未锁单的拼单可进入 `EXPIRED` |
| EXPIRED 状态 | 区分系统超时关闭和人工取消 |
| 异常/延迟事件 | 延迟、缺餐、联系不上、商家异常等记录为事件，不扩展主状态 |
| 并发控制规则 | 加入、锁单、取消、超时关闭、付款、取餐必须基于 MySQL 事务和状态校验 |
| Redis 辅助能力 | 防重复提交、短时锁、热点拼单缓存；不得替代 MySQL 状态 |
| RocketMQ 异步能力 | 超时检查、通知、统计聚合；不得作为核心状态源 |
| 产品化前端改版 | 重做拼单大厅和拼单详情页，使其更像学生使用的拼单产品 |
| 测试覆盖 | 补齐取消、超时、异常事件、并发、Redis、RocketMQ 幂等边界测试 |

## 8. V2 可选增强

| 能力 | 说明 |
| --- | --- |
| 通知中心 | 展示付款提醒、取餐变化、异常事件提醒 |
| 热门拼单推荐 | 基于拼单类型、时间段、参与人数做轻量排序 |
| 更细费用项 | 配送费、包装费、平台红包等可单独建模 |
| 管理视图 | 面向演示或测试的数据查看，不作为学生主体验 |
| 校园身份对接 | 后续可接统一身份认证，V2 不强制 |
| 统计图表增强 | 类型趋势、节省金额趋势、热门商家统计 |

## 9. 暂不实现

- 真实支付、真实退款；
- 真实外卖商家接口；
- 商家入驻和商品库；
- 即时聊天；
- 地图定位和实时配送轨迹；
- 复杂推荐系统；
- 分布式事务；
- 微服务拆分；
- 复杂 RBAC 或多级运营后台。

## 10. 核心状态模型

### 10.1 拼单主状态

```text
CREATED
LOCKED
ORDERED
DELIVERING
ARRIVED
PICKED_UP
FINISHED
CANCELLED
EXPIRED
```

`EXPIRED` 是 V2 新增状态，只用于系统超时关闭。延迟不进入主状态，统一记录为异常/履约事件。

### 10.2 `CANCELLED` 与 `EXPIRED` 区别

| 状态 | 触发方 | 典型场景 | 是否需要原因 | 后续处理 |
| --- | --- | --- | --- | --- |
| `CANCELLED` | 发起人 | 不想拼了、商家不接单、成员协商取消、已锁单后无法继续 | 必须 | 展示取消原因；已付款提示线下处理 |
| `EXPIRED` | 系统任务 | `CREATED` 超过截止时间仍未锁单 | 系统原因 | 从大厅可加入列表移除；不可继续加入 |

### 10.3 付款状态

```text
UNPAID
PAID
CONFIRMED
REFUNDED
```

付款仍是线下付款标记，不接入真实支付。取消后不自动退款，只记录和展示线下处理状态。

### 10.4 取餐状态

```text
WAITING_ORDER
WAITING_DELIVERY
ARRIVED
PICKED_UP
DISTRIBUTED
```

取餐状态推进到 `DISTRIBUTED` 后，拼单主状态同步为 `FINISHED`。

## 11. 权限规则

| 操作 | 允许角色 | 关键限制 |
| --- | --- | --- |
| 发起拼单 | 登录用户 | 必须填写标题、类型、商家、取餐地点、截止时间 |
| 加入拼单 | 登录用户 | 仅 `CREATED` 且未超时、未满员 |
| 锁单 | 发起人 | 仅 `CREATED`，锁单时重新汇总金额 |
| 取消拼单 | 发起人 | `CREATED`、`LOCKED`、`ORDERED` 可取消；`FINISHED`、`EXPIRED` 不可取消 |
| 超时关闭 | 系统任务 | 仅 `CREATED` 且当前时间超过 `deadlineTime` |
| 标记付款 | 参与者本人 | 仅自己的参与记录 |
| 确认付款 | 发起人 | 只能确认本拼单成员 |
| 指定取餐人 | 发起人 | 取餐人必须是本拼单参与者 |
| 更新取餐状态 | 发起人或取餐人 | 必须按顺序推进 |
| 记录延迟/异常 | 发起人或取餐人 | 记录为事件，不直接改变主状态 |

## 12. 功能需求

### 12.1 拼单大厅

V2 大厅应优先服务“快速判断能不能加入”：

- 顶部突出当前可加入拼单、即将截止、我参与的进行中拼单；
- 卡片展示类型、商家、取餐地点、截止倒计时、人数、满减进度、发起人、状态；
- 支持类型筛选、状态筛选、关键词搜索；
- `CREATED` 且未超时为主要加入入口；
- `LOCKED`、`ORDERED`、`DELIVERING`、`ARRIVED` 可作为围观/查看进度；
- `FINISHED`、`CANCELLED`、`EXPIRED` 默认进入历史，不在主推荐流突出展示。

### 12.2 拼单详情页

V2 详情页应成为拼单协同工作台：

- 顶部显示主状态、截止倒计时、取餐地点和操作按钮；
- 中部显示满减进度、成员清单、餐品明细、金额分摊；
- 付款区按成员展示 `UNPAID/PAID/CONFIRMED/REFUNDED`；
- 取餐区展示取餐人、取餐状态、时间线；
- 事件区展示取消、超时、延迟、缺餐、联系不上等记录；
- 操作区根据当前用户角色展示加入、锁单、付款、确认、取消、指定取餐人、更新取餐状态、记录异常。

### 12.3 取消拼单

- 发起人可取消尚未完成且未超时关闭的拼单；
- 取消必须填写 `cancelReason`；
- 已有人付款或确认付款时，取消响应必须提示“需线下处理退款/转账”；
- 取消后不可加入、不可锁单、不可继续付款或取餐；
- 取消动作写入状态日志，并建议写入业务事件。

### 12.4 超时自动关闭

- 对 `CREATED` 且 `deadlineTime < now` 的拼单执行关闭；
- 超时关闭结果为 `EXPIRED`；
- `EXPIRED` 不等于发起人取消，不使用 `cancelReason`；
- RocketMQ 可投递延迟消息触发检查，也允许后端定时任务兜底；
- 消费者必须重新查 MySQL 并校验当前状态，不能只凭消息改状态。

### 12.5 延迟/异常事件

V2 不把延迟扩展成主状态。以下情况记录为事件：

- 商家出餐延迟；
- 外卖配送延迟；
- 取餐人临时变更；
- 缺餐、错餐；
- 联系不上成员；
- 取餐地点临时变更；
- 付款争议或需要线下退款。

事件应展示在详情页时间线中，便于成员理解当前情况。

### 12.6 并发控制

- 加入拼单、锁单、取消、超时关闭、付款、取餐状态推进都必须在 MySQL 事务中完成；
- 更新时必须带当前状态条件，例如只允许 `status = CREATED` 的记录被锁单或过期；
- 人数和金额以数据库重新汇总为准，不信任前端汇总；
- Redis 可做防重复提交和短时锁，但不能作为最终判断；
- Redis 锁失败时可以拒绝快速重复请求，Redis 不可用时核心一致性仍由 MySQL 兜底。

### 12.7 RocketMQ 异步消息

RocketMQ 在 V2 中只做增强：

- 拼单截止后的超时检查消息；
- 状态变更通知消息；
- 数据看板统计聚合消息；
- 异常事件通知消息。

RocketMQ 不保存最终业务状态，不替代 MySQL 事务，不参与金额最终计算。

## 13. 非功能性需求

- 金额计算必须使用 `BigDecimal`；
- 所有状态流转必须后端校验；
- 核心状态以 MySQL 为准；
- Redis 缓存必须可失效、可重建；
- RocketMQ 消费必须幂等；
- 取消、超时、异常事件必须可追溯；
- 前端移动端和窄屏场景下必须可用；
- 接口错误信息要能指导用户下一步操作。

## 14. 验收标准

| 类别 | 验收标准 |
| --- | --- |
| 主流程 | 从发起到加入、锁单、付款、取餐、分发完成可闭环 |
| 取消 | 发起人取消后拼单不可继续加入或推进，原因可见 |
| 超时 | 超过截止时间未锁单的拼单可进入 `EXPIRED`，与 `CANCELLED` 区分 |
| 异常事件 | 延迟和异常以事件展示，不污染主状态 |
| 并发 | 重复加入、锁单与加入并发、取消与付款并发均有后端校验 |
| Redis | 防重复提交、热点缓存和短时锁有明确降级边界 |
| RocketMQ | 超时检查和通知消费幂等，不作为状态源 |
| 前端 | 大厅和详情页体现校园拼单产品体验，不是管理后台表格堆叠 |
| 测试 | 覆盖正常流程、状态拒绝、权限拒绝、金额边界、并发和异步幂等 |
