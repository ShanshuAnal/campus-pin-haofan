# 校园拼好饭系统需求说明

## 1. 项目背景

高校学生在外卖、食堂、奶茶、夜宵等场景中经常通过群聊临时拼单。现有做法通常依赖微信群、QQ群或口头沟通，容易出现以下问题：

- 拼单信息分散在聊天记录中，后加入的成员难以快速了解规则和进度；
- 满减门槛、配送费、包装费和优惠分摊需要人工计算，容易出错；
- 每个人是否已付款、是否已被确认付款不透明；
- 取餐人、取餐时间、分发状态难以及时同步；
- 拼单发起人需要反复统计人数、金额、备注和付款状态，沟通成本高。

校园拼好饭系统用于把这些临时协作流程结构化，重点解决拼单协同、满减进度、优惠分摊、付款标记和取餐状态同步问题。

系统不是外卖平台，不接入真实商家接口，不接入真实支付接口，不做即时聊天。

## 2. 项目意义与价值

本项目的价值在于降低校园拼单的组织成本，使拼单过程可记录、可计算、可追踪。

对学生：

- 快速查看可加入的拼单；
- 清楚知道拼单截止时间、满减进度和自己的应付金额；
- 可以标记付款并查看取餐状态；
- 减少群聊刷屏和重复确认。

对拼单发起人：

- 集中管理成员、餐品、金额和备注；
- 系统自动计算优惠分摊和尾差；
- 清楚查看付款标记与确认状态；
- 统一维护取餐和分发进度。

对课程项目：

- 业务闭环明确，适合展示前后端分离、数据库设计、状态流转、金额计算和接口联调；
- 范围可控，不依赖真实第三方平台；
- 可在 MVP 基础上扩展 Redis、RocketMQ 等增强能力。

## 3. 用户角色

### 3.1 普通学生

普通学生是系统主要使用者，可以浏览拼单、加入拼单、提交点餐信息、查看金额分摊、标记付款和确认取餐。

### 3.2 拼单发起人

拼单发起人是创建拼单的学生，负责维护拼单基础信息、锁定拼单、确认付款、指定取餐人、更新主要履约状态和结束拼单。

### 3.3 取餐人

取餐人可以是拼单发起人，也可以是发起人指定的成员。取餐人负责同步取餐状态，例如已下单、配送中、已到达、已取餐、已分发。

### 3.4 系统管理员

MVP 阶段不重点建设后台管理系统。系统管理员角色可作为增强范围，用于查看异常拼单、处理测试数据和维护基础配置。

## 4. 核心业务流程

MVP 主流程如下：

```text
登录
-> 发起拼单
-> 成员加入
-> 凑单计算
-> 锁定拼单
-> 优惠分摊
-> 标记付款
-> 指定取餐人
-> 更新取餐状态
-> 完成拼单
```

核心状态建议：

- 拼单状态：`CREATED`、`LOCKED`、`ORDERED`、`DELIVERING`、`ARRIVED`、`PICKED_UP`、`FINISHED`、`CANCELLED`。
- 付款状态：`UNPAID`、`PAID`、`CONFIRMED`、`REFUNDED`。
- 取餐状态：`WAITING_ORDER`、`WAITING_DELIVERY`、`ARRIVED`、`PICKED_UP`、`DISTRIBUTED`。

状态流转必须由后端校验，前端按钮显示不能作为业务安全边界。

## 6. 详细功能需求

### 6.1 用户与登录

- 用户可以使用简化账号登录系统。
- 系统需要识别当前用户，用于判断是否为拼单发起人、成员或取餐人。
- MVP 阶段不要求接入学校统一身份认证。
- 登录态可以使用简化 JWT 实现。

### 6.2 拼单大厅

- 展示当前可加入或可查看的拼单列表。
- 列表应展示拼单标题、类型、发起人、截止时间、当前人数、满减进度和状态。
- 支持按拼单状态、类型或关键词进行基础筛选。
- 已取消或已完成拼单默认不作为主要推荐内容。

### 6.3 发起拼单

- 发起人可以创建拼单，填写拼单名称、类型、商家或窗口名称、截止时间、人数限制、满减门槛、优惠金额和备注。
- 拼单创建后初始状态为 `CREATED`。
- 只有发起人可以取消未完成拼单或锁定拼单。
- 拼单被锁定后，普通成员不能继续加入或修改点餐内容。

### 6.4 加入拼单

- 学生可以在 `CREATED` 状态下加入拼单。
- 加入时需要填写餐品名称、金额、数量和备注。
- 同一个用户不能重复加入同一个拼单。
- 点餐金额必须大于 0。
- 拼单人数不能超过最大人数限制。

### 6.5 满减进度与优惠分摊

- 系统需要展示当前总金额和满减进度。
- 达到满减门槛后，系统按参与者原始金额占比分摊优惠。
- 所有金额计算必须使用 `BigDecimal`。
- 禁止使用 `double` 或 `float` 处理金额。
- 金额统一保留两位小数。
- 分摊结果必须保证总分摊金额与订单总金额一致。
- 尾差由拼单发起人承担或补齐，并在计算规则中保持一致。

### 6.6 锁单与下单

- 发起人可以手动锁定拼单。
- 拼单达到截止时间后，后续可扩展为自动锁单或过期处理。
- 锁单后系统生成最终金额分摊结果。
- 发起人完成外部平台或线下实际下单后，可以将状态更新为 `ORDERED`。

### 6.7 付款标记

- 参与者可以标记自己已付款。
- 发起人可以确认成员付款。
- 付款状态只做模拟标记，不接入真实支付。
- 成员标记已付款不等同于发起人确认付款。
- 系统需要记录付款标记时间和确认状态。

### 6.8 取餐协同

- 发起人可以指定取餐人。
- 取餐人或发起人可以更新取餐状态。
- 系统需要展示预计到达、已到达、已取餐、已分发等状态。
- 取餐状态更新必须校验当前拼单状态和操作者权限。

### 6.9 我的拼单

- 用户可以查看自己发起的拼单。
- 用户可以查看自己参与的拼单。
- 列表应显示拼单状态、个人应付金额、付款状态和取餐状态。

### 6.10 基础统计

- MVP 可展示简单统计，例如参与人数、拼单总金额、已付款人数。
- 更复杂的数据看板放入增强功能范围。

## 7. 非功能性需求

### 7.1 数据一致性

- 拼单状态、付款状态、取餐状态必须由后端统一校验。
- 金额分摊结果必须可复核。
- MySQL 是订单、成员、付款和取餐状态的最终数据源。

### 7.2 可用性

- 页面流程应围绕学生快速发起和加入拼单设计。
- 关键状态应有明确提示。
- 表单错误应清楚说明原因，例如金额非法、人数已满、拼单已锁定。

### 7.3 安全性

- 后端必须校验当前用户是否有权限执行操作。
- 普通成员不能锁单、取消拼单或确认他人付款。
- 不依赖前端隐藏按钮实现权限控制。

### 7.4 性能

- MVP 阶段优先保证核心流程稳定。
- Redis 可作为列表缓存或防重复提交增强，但不能作为主流程硬依赖。
- 数据库查询应避免明显的全表扫描风险，具体索引在数据库设计阶段确定。

### 7.5 可维护性

- 接口、数据库、状态枚举和金额规则应有文档记录。
- 需求变更必须同步影响的接口、数据库、前端页面和测试用例。
- LLM 辅助开发过程需要记录，便于课程汇报和复盘。

## 8. MVP 范围

MVP 必须实现：

- 简化登录；
- 拼单大厅；
- 发起拼单；
- 加入拼单；
- 锁定拼单；
- 满减进度展示；
- 优惠分摊和尾差处理；
- 付款标记和发起人确认；
- 指定取餐人；
- 取餐状态更新；
- 我的拼单；
- 基础异常提示；
- 核心流程测试说明。

MVP 必须保证不依赖 Redis 和 RocketMQ 也能运行。

## 9. 增强功能范围

增强功能可在 MVP 稳定后评估：

- Redis 缓存拼单大厅和热门拼单详情；
- Redis 防重复提交或短时互斥；
- RocketMQ 处理拼单截止后的异步过期；
- RocketMQ 处理状态变更通知或异步统计；
- 数据看板；
- 管理后台；
- 更丰富的筛选、排序和历史统计；
- 校园身份认证对接；
- 站内消息或通知中心。

增强功能不得影响 MVP 主流程可运行性。

## 10. 暂不实现功能

以下功能暂不实现：

- 真实支付；
- 真实退款；
- 真实外卖商家接口；
- 商家入驻系统；
- 地图定位和实时配送轨迹；
- 即时聊天；
- 短信通知；
- 复杂推荐系统；
- 多校区大型运营后台；
- 分布式事务；
- 微服务架构。

## 12. 典型使用场景

### 场景一：奶茶拼单凑满减

1. 学生 A 创建奶茶拼单，设置满 60 减 10、截止时间 15 分钟后。
2. 学生 B、C、D 加入拼单，分别填写饮品和金额。
3. 系统展示当前总金额和距离满减还差多少。
4. 达到满减后，系统按金额占比分摊优惠。
5. 发起人锁单并下单。
6. 成员标记付款，发起人确认。
7. 取餐人更新已到达和已分发状态。
8. 拼单完成。

### 场景二：夜宵拼单但人数已满

1. 发起人设置最大参与人数为 4。
2. 第 4 位成员加入后，拼单达到人数上限。
3. 第 5 位用户尝试加入时，系统拒绝并提示人数已满。

### 场景三：拼单已锁定后继续修改

1. 发起人锁定拼单。
2. 成员尝试修改餐品金额。
3. 后端拒绝操作，并提示拼单已锁定。

### 场景四：付款标记与确认不同步

1. 成员标记自己已付款。
2. 发起人尚未确认。
3. 系统显示成员已标记付款，但未确认。
4. 发起人核对后确认付款，状态变为已确认。

## 13. 验收标准

### 13.1 主流程验收

- 用户可以登录并进入拼单大厅。
- 用户可以创建拼单并在列表中看到该拼单。
- 其他用户可以加入 `CREATED` 状态的拼单。
- 发起人可以锁定拼单。
- 锁定后不能继续加入或修改点餐内容。
- 系统可以展示满减进度和分摊结果。
- 成员可以标记付款，发起人可以确认付款。
- 发起人可以指定取餐人并更新取餐状态。
- 拼单可以进入完成状态。

### 13.2 金额验收

- 金额计算使用 `BigDecimal`。
- 优惠分摊后，各成员应付金额之和等于订单实际总金额。
- 小数尾差有明确处理规则。
- 非法金额会被拒绝。

### 13.3 状态验收

- 非法状态流转会被拒绝。
- `FINISHED` 和 `CANCELLED` 状态不能继续修改。
- 非发起人不能执行发起人专属操作。
- 前端按钮控制之外，后端仍能拒绝非法操作。

### 13.4 文档验收

- 需求说明文档覆盖项目背景、价值、角色、流程、功能、MVP 和验收标准。
- 后续 API 文档、数据库设计和测试用例应与本文档保持一致。
- Redis 和 RocketMQ 仅作为增强能力描述，不作为 MVP 主流程依赖。

每次使用 LLM 进行需求、设计、编码、测试或排错时，应记录：

- 使用日期；
- 使用阶段；
- 使用工具；
- Prompt 摘要；
- 生成或修改的内容；
- 人工审查和调整点；
- 验证方式；
- 模型输出的局限或问题。

记录应客观，不夸大模型能力。涉及金额计算、状态流转、接口契约、数据库结构的 LLM 产出必须经过人工审查。
