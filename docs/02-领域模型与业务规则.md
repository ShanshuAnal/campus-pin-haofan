# 领域模型与业务规则

## 1. 文档目的

本文档用于说明校园拼好饭系统的核心领域对象、业务状态、金额计算规则、异常场景和可选增强边界，为后续数据库设计、API 文档、后端实现、前端联调和测试用例提供统一业务依据。

本文档不包含代码、SQL 表结构或工程脚手架。

## 2. 业务边界

系统定位为校园内部拼单协同工具，覆盖外卖、食堂、奶茶、夜宵等拼单场景。

系统重点支持：

- 拼单发起；
- 成员加入；
- 满减进度展示；
- 优惠分摊；
- 付款标记；
- 发起人确认付款；
- 指定取餐人；
- 取餐状态同步；
- 拼单完成。

系统不支持：

- 真实支付；
- 真实退款；
- 真实商家接口；
- 即时聊天；
- 地图定位；
- 真实配送跟踪。

Redis 和 RocketMQ 仅作为可选增强点，不作为 MVP 主流程硬依赖。

## 3. 核心领域对象

### 3.1 用户 User

表示系统中的学生用户。

主要职责：

- 登录系统；
- 发起拼单；
- 加入拼单；
- 标记付款；
- 被指定为取餐人；
- 查看自己发起或参与的拼单。

关键属性建议：

- 用户 ID；
- 昵称或姓名；
- 联系方式或账号；
- 用户状态；
- 创建时间；
- 更新时间。

业务规则：

- 用户必须登录后才能发起或加入拼单。
- 同一用户不能重复加入同一拼单。
- 用户是否为拼单发起人决定其可执行操作范围。

### 3.2 拼单 GroupOrder

表示一次拼饭协同活动，是系统最核心的聚合对象。

主要职责：

- 记录拼单基础信息；
- 管理拼单成员；
- 维护拼单状态；
- 维护满减规则和金额汇总；
- 指定取餐人；
- 推进下单、取餐和完成流程。

关键属性建议：

- 拼单 ID；
- 拼单标题；
- 拼单类型：外卖、食堂、奶茶、夜宵等；
- 商家或窗口名称；
- 发起人 ID；
- 截止时间；
- 最大人数；
- 当前人数；
- 满减门槛；
- 优惠金额；
- 拼单状态；
- 取餐人 ID；
- 备注；
- 创建时间；
- 更新时间。

业务规则：

- 拼单创建后初始状态为 `CREATED`。
- 只有 `CREATED` 状态允许普通成员加入。
- `LOCKED` 后不能继续加入或修改点餐内容。
- `FINISHED` 和 `CANCELLED` 状态不能继续修改。
- 只有发起人可以锁单、取消拼单、指定取餐人和推进主要履约状态。

### 3.3 拼单参与者 GroupOrderMember

表示用户加入某个拼单后的参与记录。

主要职责：

- 关联用户与拼单；
- 记录成员点餐金额；
- 记录个人优惠分摊；
- 记录个人应付金额；
- 记录付款状态。

关键属性建议：

- 参与记录 ID；
- 拼单 ID；
- 用户 ID；
- 原始金额；
- 分摊优惠金额；
- 应付金额；
- 付款状态；
- 付款标记时间；
- 付款确认时间；
- 备注；
- 创建时间；
- 更新时间。

业务规则：

- 一个用户在同一拼单中只能存在一条参与记录。
- 原始金额必须大于 0。
- 成员的金额结果由系统计算，不应由前端直接决定。
- 成员标记付款后，还需要发起人确认才算最终确认。

### 3.4 餐品条目 MealItem

表示参与者提交的具体点餐内容。

主要职责：

- 记录餐品名称、数量、单价或小计；
- 记录口味、备注等信息；
- 支持拼单详情展示和发起人下单参考。

关键属性建议：

- 餐品条目 ID；
- 拼单 ID；
- 参与记录 ID；
- 餐品名称；
- 数量；
- 单价；
- 小计金额；
- 备注。

业务规则：

- 餐品小计必须大于 0。
- 同一参与者可以有多个餐品条目。
- 锁单后普通成员不能新增、删除或修改餐品条目。

### 3.5 付款记录 PaymentRecord

表示付款标记和确认过程。

主要职责：

- 记录成员付款标记；
- 记录发起人确认动作；
- 保留付款状态变化信息。

关键属性建议：

- 付款记录 ID；
- 拼单 ID；
- 参与记录 ID；
- 用户 ID；
- 付款状态；
- 标记付款时间；
- 确认人 ID；
- 确认时间；
- 备注。

业务规则：

- 系统不接入真实支付。
- 付款记录仅表示线下转账、红包或其他外部付款后的状态标记。
- 普通成员只能标记自己的付款状态。
- 发起人可以确认成员付款。
- 未确认付款不应被展示为最终已确认。

### 3.6 取餐记录 PickupRecord

表示拼单履约和取餐分发过程。

主要职责：

- 记录取餐人；
- 记录取餐状态；
- 记录预计到达、已到达、已取餐、已分发等信息。

关键属性建议：

- 取餐记录 ID；
- 拼单 ID；
- 取餐人 ID；
- 取餐状态；
- 预计到达时间；
- 实际到达时间；
- 取餐完成时间；
- 分发完成时间；
- 备注。

业务规则：

- 取餐人由发起人指定。
- 发起人或取餐人可以更新取餐状态。
- 取餐状态更新必须与拼单状态匹配。
- 拼单未下单前不应进入配送或取餐状态。

### 3.7 操作记录 OperationLog

表示关键业务操作的记录。

主要职责：

- 记录拼单状态变化；
- 记录付款确认；
- 记录取餐状态变化；
- 支持后续问题排查和课程演示。

关键属性建议：

- 操作记录 ID；
- 操作人 ID；
- 操作对象类型；
- 操作对象 ID；
- 操作类型；
- 操作前状态；
- 操作后状态；
- 操作时间；
- 备注。

业务规则：

- MVP 可先记录核心状态变化。
- 增强阶段可扩展为更完整的审计日志。

## 4. 对象关系

核心关系如下：

- 一个用户可以发起多个拼单。
- 一个用户可以参与多个拼单。
- 一个拼单只有一个发起人。
- 一个拼单可以有多个参与者。
- 一个参与者可以有多个餐品条目。
- 一个参与者对应自己的付款状态。
- 一个拼单最多指定一个当前取餐人。
- 一个拼单可以有多条状态操作记录。

简化关系：

```text
User 1 -> N GroupOrder
User N -> N GroupOrder, through GroupOrderMember
GroupOrder 1 -> N GroupOrderMember
GroupOrderMember 1 -> N MealItem
GroupOrderMember 1 -> N PaymentRecord
GroupOrder 1 -> 0..1 PickupRecord
GroupOrder 1 -> N OperationLog
```

## 5. 拼单状态流转

### 5.1 状态定义

```text
CREATED      进行中，允许加入
LOCKED       已锁单，不允许继续加入
ORDERED      已下单
DELIVERING   配送中
ARRIVED      已到达
PICKED_UP    已取餐
FINISHED     已完成
CANCELLED    已取消
```

MVP 阶段不实现 `EXPIRED` 拼单状态。拼单超过截止时间但未继续推进时，由发起人手动取消，状态使用 `CANCELLED`。自动过期可作为 RocketMQ 增强功能后置评估，后续如引入 `EXPIRED`，必须先同步更新领域规则、API 文档、数据库状态说明、后端枚举和测试用例。

### 5.2 允许流转

| 当前状态 | 目标状态 | 操作人 | 说明 |
| --- | --- | --- | --- |
| CREATED | LOCKED | 发起人 | 锁定拼单，生成最终金额分摊 |
| CREATED | CANCELLED | 发起人 | 取消未锁定拼单 |
| LOCKED | ORDERED | 发起人 | 发起人完成外部下单后标记 |
| LOCKED | CANCELLED | 发起人 | 未实际下单前可取消 |
| ORDERED | DELIVERING | 发起人或取餐人 | 外部订单进入配送或等待取餐过程 |
| ORDERED | ARRIVED | 发起人或取餐人 | 食堂或自取场景可直接到达 |
| DELIVERING | ARRIVED | 发起人或取餐人 | 配送到达 |
| ARRIVED | PICKED_UP | 发起人或取餐人 | 已取到餐 |
| PICKED_UP | FINISHED | 发起人 | 分发完成后结束拼单 |

### 5.3 禁止流转

- `FINISHED` 不能回退到任何状态。
- `CANCELLED` 不能继续推进。
- 不能从 `CREATED` 直接到 `FINISHED`。
- 不能绕过 `LOCKED` 直接下单或完成。
- 普通成员不能推进拼单主状态。
- 拼单状态变更不能只依赖前端按钮限制，必须由后端校验。

## 6. 付款状态流转

### 6.1 状态定义

```text
UNPAID       未付款
PAID         成员已标记付款
CONFIRMED    发起人已确认
REFUNDED     已退款或已撤销付款标记
```

### 6.2 允许流转

| 当前状态 | 目标状态 | 操作人 | 说明 |
| --- | --- | --- | --- |
| UNPAID | PAID | 成员本人 | 成员标记自己已付款 |
| PAID | CONFIRMED | 发起人 | 发起人核对后确认 |
| PAID | UNPAID | 成员本人或发起人 | 误标记时撤销 |
| CONFIRMED | REFUNDED | 发起人 | 线下退款或订单取消后的记录 |

### 6.3 付款规则

- 付款状态只做模拟标记，不接入真实支付。
- 成员只能标记自己的付款状态。
- 发起人可以确认所有成员付款。
- `PAID` 不等于最终确认，只有 `CONFIRMED` 表示发起人已确认。
- 拼单取消后，已付款或已确认记录需要明确展示后续线下处理状态。

## 7. 取餐状态流转

### 7.1 状态定义

```text
WAITING_ORDER      待下单
WAITING_DELIVERY   待配送或待出餐
ARRIVED            已到达
PICKED_UP          已取餐
DISTRIBUTED        已分发
```

### 7.2 允许流转

| 当前状态 | 目标状态 | 操作人 | 说明 |
| --- | --- | --- | --- |
| WAITING_ORDER | WAITING_DELIVERY | 发起人 | 已完成外部下单 |
| WAITING_DELIVERY | ARRIVED | 发起人或取餐人 | 餐品已到达或可取 |
| ARRIVED | PICKED_UP | 发起人或取餐人 | 已取到餐 |
| PICKED_UP | DISTRIBUTED | 发起人或取餐人 | 已分发给成员 |

### 7.3 取餐规则

- 取餐人必须由发起人指定。
- 取餐状态不能早于拼单履约状态。
- 拼单未下单前不能标记已到达或已取餐。
- 分发完成后，发起人可以将拼单标记为 `FINISHED`。

## 8. 金额计算规则

### 8.1 金额字段

所有金额计算必须使用 `BigDecimal`。禁止使用 `double` 或 `float` 处理金额。

金额统一保留两位小数。数据库金额字段后续应使用 `decimal(10,2)`。

### 8.2 基础金额

参与者原始金额：

```text
member_original_amount = 该成员所有餐品小计之和
```

拼单原始总金额：

```text
order_original_amount = 所有成员 member_original_amount 之和
```

实际优惠金额：

```text
actual_discount_amount =
  如果 order_original_amount >= discount_threshold，则为 configured_discount_amount
  否则为 0
```

拼单实际应付总金额：

```text
order_payable_amount = order_original_amount - actual_discount_amount
```

### 8.3 优惠分摊

优惠按参与者原始金额占比分摊：

```text
member_discount_amount =
  actual_discount_amount * member_original_amount / order_original_amount
```

成员实际应付：

```text
member_payable_amount = member_original_amount - member_discount_amount
```

规则：

- 未达到满减门槛时，所有成员分摊优惠为 0。
- 达到满减门槛后，按成员原始金额占比计算分摊优惠。
- 单个成员应付金额不能小于 0。
- 分摊后所有成员应付金额之和必须等于拼单实际应付总金额。
- 小数尾差由拼单发起人承担或补齐。
- 尾差处理策略必须固定，不能每次计算随机分配。

### 8.4 配送费和包装费

MVP 阶段可先将配送费、包装费计入成员提交的原始金额或由发起人手动分摊。

增强阶段可支持：

- 配送费按人数均摊；
- 包装费按餐品归属计入；
- 平台红包或额外优惠按金额占比分摊。

任何费用分摊规则都必须保证最终总额一致。

## 9. 主要异常场景

### 9.1 拼单异常

- 拼单不存在；
- 拼单已取消；
- 拼单已完成；
- 拼单已锁定但用户仍尝试加入；
- 拼单人数已满；
- 拼单已过截止时间；
- 非发起人尝试锁单、取消或推进主状态；
- 发起人尝试取消已完成拼单；
- 直接从未锁定状态跳到完成状态。

### 9.2 成员异常

- 未登录用户尝试加入拼单；
- 同一用户重复加入同一拼单；
- 用户尝试修改他人的点餐信息；
- 用户尝试退出已锁定拼单；
- 用户提交空餐品或非法金额；
- 用户提交金额为 0 或负数。

### 9.3 金额异常

- 优惠金额大于拼单原始总金额；
- 满减门槛为空或小于等于 0；
- 分摊后成员应付金额小于 0；
- 成员应付金额汇总与订单应付总金额不一致；
- 使用浮点类型导致精度误差；
- 重复计算导致金额结果被覆盖且不可追踪。

### 9.4 付款异常

- 用户标记他人付款；
- 非发起人确认付款；
- 未加入拼单的用户标记付款；
- 已确认付款被普通成员撤销；
- 拼单取消后付款状态未提示线下处理。

### 9.5 取餐异常

- 未指定取餐人就更新取餐状态；
- 非发起人或非取餐人更新取餐状态；
- 未下单却标记已到达；
- 未到达却标记已取餐；
- 未取餐却标记已分发；
- 拼单已取消后继续更新取餐状态。

## 10. Redis 与 RocketMQ 可选增强点

### 10.1 Redis

可选场景：

- 拼单大厅列表缓存；
- 热门拼单详情缓存；
- 登录 token/session 缓存；
- 防重复提交；
- 短时互斥锁；
- 简单限流。

边界：

- Redis 不作为订单、参与者、付款或取餐状态的最终存储。
- Redis 不可用时，MVP 主流程仍必须能通过 MySQL 运行。
- 缓存必须有过期策略，且可以从 MySQL 恢复。

### 10.2 RocketMQ

可选场景：

- 拼单截止后的异步过期处理；
- 状态变更通知；
- 异步统计；
- 低优先级日志或事件处理。

边界：

- RocketMQ 不替代同步业务校验。
- 消息失败不能导致订单无法完成。
- 消费逻辑必须幂等。
- RocketMQ 不可用时，MVP 主流程仍可通过同步流程或人工操作推进。
