# 校园拼好饭系统 V2 领域模型与业务规则

## 1. 文档目标

本文定义校园拼好饭系统 V2 的核心领域对象、状态流转、金额规则、操作权限、并发控制和异步增强边界。

V2 设计保留当前 MVP 已完成能力，并将其纳入更完整的校园拼单协同闭环。后端、前端、SQL 和测试会话实现功能时，应以本文作为业务规则依据。

## 2. 领域边界

系统定位为校园拼单协同系统，不是外卖平台。

系统负责：

- 发起拼单、加入拼单、锁定拼单；
- 记录成员餐品、金额、优惠和分摊结果；
- 标记付款和确认付款；
- 指定取餐人并同步取餐状态；
- 记录取消、超时、延迟和异常履约事件；
- 通过 Redis、RocketMQ 提升体验和异步处理能力。

系统不负责：

- 真实外卖下单；
- 真实支付扣款；
- 商家系统对接；
- 即时聊天；
- 复杂商户、配送和财务清结算。

## 3. 核心对象

### 3.1 User

用户代表高校学生账号。

核心职责：

- 登录认证；
- 发起拼单；
- 加入拼单；
- 标记付款；
- 被指定为取餐人；
- 查看个人拼单、待付款和历史记录。

### 3.2 GroupOrder

拼单是系统主聚合根，承载一次校园拼单协同。

核心字段概念：

- 发起人；
- 店铺名称；
- 拼单标题；
- 约定取餐地点；
- 截止时间；
- 凑单门槛；
- 优惠金额；
- 当前总金额；
- 拼单主状态；
- 取餐人；
- 取消原因；
- 过期时间；
- 并发版本号。

### 3.3 OrderParticipant

拼单成员表示用户参与某个拼单的记录。

核心职责：

- 标识用户是否已加入拼单；
- 维护成员原始金额、优惠分摊金额、应付金额；
- 维护成员付款状态；
- 支撑“我的拼单”“待付款”“历史拼单”查询。

一个 `group_order` 可以有多个 `order_participant`；一个用户在同一个拼单中只能有一条有效参与记录。

### 3.4 MealItem

餐品条目表示成员在拼单中的具体点餐内容。

核心职责：

- 记录餐品名称、单价、数量、小计；
- 支撑订单明细展示；
- 支撑金额汇总和优惠分摊。

### 3.5 PaymentRecord

付款记录表示成员的付款标记和发起人的确认结果。

核心职责：

- 记录成员标记已付款；
- 记录发起人确认付款；
- 保留付款备注和操作时间；
- 支撑后续争议和复盘。

系统不接入真实支付，付款状态只代表线下付款协同标记。

### 3.6 PickupRecord

取餐记录表示拼单履约状态。

核心职责：

- 记录取餐人；
- 记录实际取餐地点；
- 维护取餐状态；
- 支撑从“已下单”到“已分发”的协同流程。

当取餐状态推进到 `DISTRIBUTED` 后，拼单主状态同步为 `FINISHED`。

### 3.7 GroupOrderEvent

拼单事件是 V2 新增的履约事件模型，用于记录取消、超时、延迟、异常和备注。

事件不替代主状态，也不强行扩大主状态枚举。

典型事件：

- `CANCELLED`：人工取消；
- `EXPIRED`：超时关闭；
- `DELAY_REPORTED`：延迟上报；
- `MERCHANT_DELAY`：商家制作延迟；
- `DELIVERY_DELAY`：配送或取餐延迟；
- `PICKUP_EXCEPTION`：取餐异常；
- `ITEM_MISSING`：餐品缺失；
- `CONTACT_FAILED`：联系失败；
- `PAYMENT_DISPUTE`：付款争议；
- `NOTE`：普通备注。

### 3.8 NotificationRecord

通知记录用于异步提醒和消息回放。

V2 中通知仍是增强能力，不是核心状态源。通知失败不能改变拼单真实状态。

## 4. 聚合关系

```text
User
  ├─ 发起 GroupOrder
  ├─ 参与 OrderParticipant
  └─ 操作 PaymentRecord / PickupRecord / GroupOrderEvent

GroupOrder
  ├─ OrderParticipant
  │    └─ MealItem
  ├─ PaymentRecord
  ├─ PickupRecord
  ├─ GroupOrderEvent
  └─ NotificationRecord
```

规则：

- `GroupOrder` 是拼单聚合根。
- 拼单状态、金额汇总、参与成员变更必须在同一事务中校验和落库。
- Redis、RocketMQ 不能成为拼单状态源。
- 任何异步任务处理前必须重新读取 MySQL 当前状态。

## 5. 主状态模型

### 5.1 拼单主状态

| 状态 | 含义 | 是否终态 |
| --- | --- | --- |
| `CREATED` | 拼单已创建，成员可加入 | 否 |
| `LOCKED` | 拼单已锁定，停止加入和修改餐品 | 否 |
| `ORDERED` | 发起人已完成线下下单 | 否 |
| `DELIVERING` | 等待配送或取餐途中 | 否 |
| `ARRIVED` | 餐品已到达约定取餐点 | 否 |
| `PICKED_UP` | 取餐人已取到餐品，等待分发 | 否 |
| `FINISHED` | 餐品已分发完成 | 是 |
| `CANCELLED` | 发起人主动取消 | 是 |
| `EXPIRED` | 系统因超时自动关闭 | 是 |

V2 可以引入 `EXPIRED`，但必须和 `CANCELLED` 区分：

- `CANCELLED` 是人工操作结果，需要记录操作人和取消原因；
- `EXPIRED` 是系统根据截止时间自动关闭的结果，需要记录触发时间和系统事件；
- 二者都是终态，终态后不能加入、锁定、付款或推进取餐。

### 5.2 推荐主状态流转

```text
CREATED
  ├─ 发起人锁定 -> LOCKED
  ├─ 发起人取消 -> CANCELLED
  └─ 超时自动关闭 -> EXPIRED

LOCKED
  ├─ 发起人标记已下单 -> ORDERED
  └─ 发起人取消 -> CANCELLED

ORDERED
  ├─ 取餐人更新配送中 -> DELIVERING
  └─ 发起人取消 -> CANCELLED

DELIVERING
  └─ 取餐人更新已到达 -> ARRIVED

ARRIVED
  └─ 取餐人更新已取餐 -> PICKED_UP

PICKED_UP
  └─ 取餐人更新已分发 -> FINISHED
```

异常、延迟、争议不新增主状态，统一记录为事件。

### 5.3 付款状态

| 状态 | 含义 |
| --- | --- |
| `UNPAID` | 未付款 |
| `PAID` | 成员已标记付款 |
| `CONFIRMED` | 发起人已确认付款 |
| `REFUNDED` | 线下退款已记录 |

规则：

- 成员只能标记自己的付款状态；
- 发起人可以确认成员付款；
- 系统不做真实支付扣款；
- 拼单终态后不允许新增付款标记，退款可作为 V2 可选增强事件记录。

### 5.4 取餐状态

| 状态 | 含义 |
| --- | --- |
| `WAITING_ORDER` | 等待发起人线下下单 |
| `WAITING_DELIVERY` | 等待配送或制作完成 |
| `ARRIVED` | 餐品已到达 |
| `PICKED_UP` | 取餐人已取到餐品 |
| `DISTRIBUTED` | 已分发给成员 |

规则：

- 取餐状态由发起人或取餐人推进；
- 取餐状态必须按顺序推进；
- 当取餐状态为 `DISTRIBUTED` 时，拼单主状态同步为 `FINISHED`；
- 取餐延迟和异常记录为 `GroupOrderEvent`，不新增取餐状态。

## 6. 操作权限

| 操作 | 允许角色 | 允许状态 | 结果 |
| --- | --- | --- | --- |
| 发起拼单 | 登录用户 | 无 | 创建 `CREATED` 拼单 |
| 加入拼单 | 登录用户 | `CREATED` | 新增参与记录和餐品 |
| 锁定拼单 | 发起人 | `CREATED` | 状态变为 `LOCKED`，计算优惠分摊 |
| 标记已下单 | 发起人 | `LOCKED` | 状态变为 `ORDERED` |
| 标记付款 | 参与成员 | `LOCKED`、`ORDERED`、`DELIVERING`、`ARRIVED`、`PICKED_UP` | 付款状态变为 `PAID` |
| 确认付款 | 发起人 | 非终态 | 成员付款状态变为 `CONFIRMED` |
| 指定取餐人 | 发起人 | `LOCKED`、`ORDERED` | 生成或更新取餐记录 |
| 更新取餐状态 | 发起人或取餐人 | `ORDERED`、`DELIVERING`、`ARRIVED`、`PICKED_UP` | 推进取餐状态和主状态 |
| 取消拼单 | 发起人 | `CREATED`、`LOCKED`、`ORDERED` | 状态变为 `CANCELLED`，记录事件 |
| 超时关闭 | 系统 | `CREATED` 且超过截止时间 | 状态变为 `EXPIRED`，记录事件 |
| 记录延迟/异常 | 发起人或取餐人 | 非终态优先 | 写入事件，不直接改变主状态 |
| 查看拼单 | 公开或登录用户 | 全状态 | 按接口权限返回 |

## 7. 金额计算规则

金额计算必须使用 Java `BigDecimal`，禁止使用 `double`、`float` 进行金额计算。

### 7.1 金额字段含义

- `originalAmount`：成员餐品原始金额；
- `totalAmount`：拼单原始总金额；
- `discountAmount`：拼单优惠总金额；
- `shareDiscountAmount`：成员分摊优惠金额；
- `payableAmount`：成员应付金额；
- `actualPaidAmount`：线下实际付款记录金额。

### 7.2 优惠分摊

V2 默认采用按成员原始金额比例分摊：

```text
成员优惠 = 拼单优惠总额 * 成员原始金额 / 拼单原始总额
成员应付 = 成员原始金额 - 成员优惠
```

规则：

- 分摊结果保留 2 位小数；
- 舍入使用 `RoundingMode.HALF_UP`；
- 最后一名成员承担尾差，确保成员应付金额合计等于拼单应付总额；
- 拼单锁定时计算并固化分摊结果；
- 锁定后禁止修改餐品和成员金额。

### 7.3 异常金额

- 取消拼单不自动生成退款逻辑；
- 已付款后取消时，系统只记录取消事件和付款状态，线下退款由成员自行处理；
- V2 可选增强可以增加退款事件，但不接入真实支付。

## 8. 并发控制规则

V2 并发控制以 MySQL 事务和状态校验为主，Redis 只作为辅助增强。

### 8.1 MySQL 主控制

必须使用：

- 数据库事务；
- 状态条件更新；
- 唯一约束；
- 必要的行级锁；
- 乐观锁版本字段。

关键场景：

- 加入拼单时校验状态仍为 `CREATED`；
- 同一用户重复加入同一拼单必须失败；
- 锁定拼单时重新计算总金额和优惠；
- 取消、超时、锁定三类操作必须互斥；
- 付款标记必须校验参与关系；
- 取餐状态推进必须校验当前状态和操作者权限。

### 8.2 Redis 辅助能力

Redis 可用于：

- 防重复提交；
- 短时业务锁；
- 热点拼单大厅缓存；
- 拼单详情短时缓存；
- accessToken 黑名单。

Redis 不得用于：

- 存储拼单最终状态；
- 替代 MySQL 事务；
- 作为金额计算来源；
- 作为唯一事件记录。

推荐 key：

| 场景 | Key |
| --- | --- |
| 防重复提交 | `idem:{userId}:{method}:{path}:{bizKey}` |
| 拼单短时锁 | `lock:group-order:{orderId}` |
| 拼单大厅缓存 | `cache:group-order:hall:{filtersHash}` |
| 拼单详情缓存 | `cache:group-order:detail:{orderId}` |
| accessToken 黑名单 | `auth:blacklist:access:{tokenHash}` |

## 9. RocketMQ 异步边界

RocketMQ 只用于增强能力，不作为核心状态源。

可用于：

- 拼单超时检查；
- 异步通知；
- 统计聚合；
- 事件投递；
- 延迟提醒。

不可用于：

- 直接决定最终拼单状态；
- 替代数据库事务；
- 作为唯一通知记录；
- 作为金额或参与记录来源。

消费者规则：

- 消费消息后必须重新读取 MySQL；
- 根据当前状态判断是否仍需处理；
- 消费逻辑必须幂等；
- 处理结果需要写入事件或日志；
- 消息失败不能导致主流程不可用。

## 10. 主要异常场景

| 场景 | 处理规则 |
| --- | --- |
| 用户重复加入 | 唯一约束和业务校验拒绝 |
| 拼单锁定时仍有人加入 | 状态条件更新和事务控制，失败方返回状态已变化 |
| 发起人取消时成员已付款 | 允许在指定状态取消，记录取消事件，线下处理退款 |
| 超时任务与发起人锁定同时发生 | MySQL 状态条件更新决定唯一成功方 |
| 取餐人延迟 | 写入延迟事件，不改变主状态 |
| 餐品缺失 | 写入异常事件，必要时发起人线下协调 |
| 付款争议 | 写入付款争议事件，不接入真实支付 |
| MQ 重复消费 | 幂等键和状态校验保证不重复变更 |
| Redis 锁失败 | 回退到 MySQL 状态校验，不影响正确性 |

## 11. V2 必做与可选增强

### V2 必做

- 取消拼单；
- 拼单超时自动关闭并引入 `EXPIRED`；
- 延迟和异常事件记录；
- MySQL 事务、状态校验和并发版本控制；
- 拼单大厅和详情页产品化交互规则；
- API、数据库、测试文档统一。

### V2 可选增强

- Redis 防重复提交；
- Redis 短时锁；
- Redis 热点缓存；
- RocketMQ 异步通知；
- RocketMQ 超时检查；
- RocketMQ 统计聚合；
- 更细的退款事件和争议处理。
