## 3. 契约与业务规则审查

### 3.1 已对齐项

- 已实现接口路径与 `docs/04-API接口文档.md` 中认证、拼单大厅、发起拼单、拼单详情、加入拼单、锁单分摊、付款标记、付款确认、我的拼单、数据看板接口基本一致。应用配置 `server.servlet.context-path=/api`，Controller 映射组合后符合 `/api/...` 基础路径。
- 用户注册和登录使用 `username/password`，`username` 映射 `user.account`，密码通过 BCrypt 哈希写入，响应不返回密码哈希。
- 发起拼单时 `creatorId` 由 token 解析，不接受前端传入。
- 加入拼单校验 `CREATED` 状态、截止时间、重复加入、人数上限和餐品金额。
- 锁单只允许发起人在 `CREATED` 状态执行，并基于 `meal_item.subtotal_amount` 重新汇总金额。
- 优惠分摊使用 `BigDecimal`，自动化测试覆盖了满减、未达满减和小数尾差场景，最终成员应付金额汇总等于订单应付总额。
- 付款标记只允许参与者本人操作；付款确认只允许发起人操作；重复标记和重复确认均拒绝并避免新增付款记录。
- `payment_record` 表结构与当前付款 VO 字段一致，自动化测试覆盖标记付款和确认付款时的记录写入。
- 指定取餐人只允许发起人操作，取餐人必须是发起人或本单参与者；取餐状态只允许发起人或取餐人按 `WAITING_ORDER -> WAITING_DELIVERY -> ARRIVED -> PICKED_UP -> DISTRIBUTED` 顺序推进。
- 取餐状态推进会同步拼单主状态：`WAITING_DELIVERY` 对应 `DELIVERING`，`ARRIVED` 对应 `ARRIVED`，`PICKED_UP` 对应 `PICKED_UP`，`DISTRIBUTED` 对应 `FINISHED`；状态变更写入 `order_status_log`。
- 我的拼单查询会先加载当前用户参与记录，再按 scope 拼接当前用户发起、参与、负责取餐、待付款或历史拼单条件；自动化测试已捕获查询条件，避免返回无关用户数据。
- 数据看板基于当前用户相关拼单聚合，自动化测试覆盖 `todayOrderCount`、`successOrderCount`、`totalSavedAmount`、金额汇总、付款人数和热门类型/店铺。
