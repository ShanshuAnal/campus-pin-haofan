# 校园拼好饭系统项目汇报材料

## 1. 项目一句话定位

校园拼好饭系统是一个面向高校学生的校园拼单协同系统，重点解决外卖、食堂、奶茶、夜宵等场景中的拼单组织、满减凑单、金额分摊、模拟支付标记和取餐协同问题。

系统不是外卖平台，不接入真实商家接口，不接入真实支付，不处理真实资金。模拟支付、模拟托管、模拟结算和模拟退款均为课程项目中的状态流转，用于表达拼单协作过程，不代表真实资金流。

## 2. 项目背景与现实意义

高校学生经常在群聊中临时拼饭、拼奶茶、拼夜宵。实际协作中常见问题包括：

- 拼单信息分散在聊天记录中，后来加入的同学难以判断是否还能参与；
- 满减门槛和优惠分摊需要人工计算，容易产生争议；
- 付款状态不透明，发起人需要反复确认谁已付款；
- 取餐进度依赖口头同步，成员不知道是否已下单、到达、取回或分发；
- 取消、超时、延迟、缺餐等异常场景缺少统一记录。

本项目的现实价值在于把“群聊临时拼单”转化为结构化协同流程：谁发起、谁加入、差多少钱满减、每个人应付多少、谁负责取餐、当前是否异常，都可以在系统中被清晰表达。

## 3. 需求说明

### 3.1 用户角色

| 角色 | 说明 | 主要操作 |
| --- | --- | --- |
| 发起人 | 创建拼单并组织下单的人 | 发起拼单、锁单、确认模拟托管、取消拼单、指定取餐人 |
| 参与者 | 加入拼单的学生 | 加入拼单、查看分摊金额、提交模拟支付 |
| 取餐人 | 被指定负责取餐的人 | 推进取餐状态、记录延迟或异常 |
| 系统任务 | 后端定时任务或 RocketMQ 消费者 | 超时关闭、异步触发、补偿扫描 |
| 测试/演示管理员 | 非学生主流程角色 | 准备数据、辅助验证和演示 |

### 3.2 核心业务流程

```text
注册/登录
-> 浏览拼单大厅
-> 发起拼单并填写发起人餐品
-> 参与者加入拼单
-> 发起人锁单
-> 系统计算满减分摊
-> 参与者提交模拟支付
-> 发起人确认模拟托管记录
-> 指定取餐人
-> 推进取餐状态
-> 完成拼单并模拟结算
```

异常流程包括发起人取消拼单、系统超时关闭、延迟/缺餐/联系失败等事件记录。

## 5. 系统架构

项目采用前后端分离结构。

```text
Vue3 前端
  -> Axios API 封装
  -> Spring Boot 3 后端 Controller
  -> Service 业务规则与事务
  -> MyBatis-Plus Mapper
  -> MySQL 8

Redis：token 黑名单、防重复提交、短时锁
RocketMQ：超时检查消息、异步增强
```

### 5.1 后端技术栈

- Java 21
- Spring Boot 3.2.12
- MyBatis-Plus 3.5.7
- MySQL 8
- Redis
- RocketMQ client 5.1.4
- Maven

后端分层包括 Controller、Service、Mapper、Entity、DTO、VO、Enum、Common、Exception、Messaging 等。

### 5.2 前端技术栈

- Vue 3
- Vite
- TypeScript
- Element Plus
- Pinia
- Axios
- Vue Router

前端页面包括登录注册、拼单大厅、发起拼单、拼单详情、我的拼单、数据看板。

## 6. 数据库设计

核心表设计围绕拼单生命周期展开：

| 表 | 作用 |
| --- | --- |
| `user` | 用户账号、昵称、状态、登录信息 |
| `user_refresh_token` | refreshToken SHA-256 摘要和作废状态 |
| `group_order` | 拼单主表，记录状态、金额、取餐点、取消和过期信息 |
| `order_participant` | 参与者金额、付款状态和备注 |
| `meal_item` | 每个参与者的餐品明细 |
| `payment_record` | 模拟支付、确认、结算、退款记录 |
| `pickup_record` | 取餐状态推进记录 |
| `order_status_log` | 主状态变化日志 |
| `group_order_event` | 取消、超时、延迟、异常和备注事件 |
| `notification_record` | 通知增强表，主流程不强依赖 |

金额字段统一使用 `decimal(10,2)`，后端计算使用 `BigDecimal`。状态字段统一使用 `varchar(32)`。`group_order` 已包含取消、超时、版本号和最近事件时间字段，并为大厅查询、超时扫描、事件查询等场景设计索引。

## 7. 接口设计

接口路径以 `/api` 为上下文前缀，核心资源使用 `/group-orders`。

| 模块 | 代表接口 |
| --- | --- |
| 认证 | `POST /api/auth/register`、`POST /api/auth/login`、`GET /api/auth/me`、`POST /api/auth/refresh`、`POST /api/auth/logout` |
| 拼单大厅 | `GET /api/group-orders` |
| 发起拼单 | `POST /api/group-orders` |
| 拼单详情 | `GET /api/group-orders/{id}` |
| 加入拼单 | `POST /api/group-orders/{id}/participants` |
| 锁单 | `POST /api/group-orders/{id}/lock` |
| 取消拼单 | `POST /api/group-orders/{id}/cancel` |
| 履约事件 | `POST /api/group-orders/{id}/events`、`GET /api/group-orders/{id}/events` |
| 模拟支付 | 当前实现为参与记录维度的 mark/confirm 接口 |
| 取餐 | 指定取餐人和推进取餐状态接口 |
| 我的拼单 | `GET /api/my/group-orders` |
| 数据看板 | `GET /api/dashboard/summary` |
| 内部超时 | `POST /api/internal/group-orders/{id}/expire-check`、`POST /api/internal/group-orders/expire-scan` |

接口设计原则是：前端只负责展示和触发操作，状态流转、金额计算、权限校验和幂等控制均由后端保证。

## 11. 重点实现说明

### 11.1 金额分摊

锁单时后端重新汇总餐品金额，判断是否达到满减门槛。优惠按成员原始金额比例分摊，尾差由固定规则处理，避免人工分摊导致争议。所有金额计算使用 `BigDecimal`，不使用浮点数。

### 11.2 状态流转

拼单主状态包括 `CREATED`、`LOCKED`、`ORDERED`、`DELIVERING`、`ARRIVED`、`PICKED_UP`、`FINISHED`、`CANCELLED`、`EXPIRED`。终态后禁止继续加入、锁单、模拟支付或推进取餐。延迟、缺餐、联系失败、支付争议等不新增主状态，而是进入事件时间线。

### 11.3 模拟资金流

本项目只做课程项目中的模拟状态流：

```text
UNPAID
-> ESCROWED：参与者提交模拟支付，进入模拟托管
-> CONFIRMED：发起人确认模拟托管记录
-> SETTLED：拼单完成后模拟结算给发起人
-> REFUNDED：取消、超时或异常终止后模拟退款
```

这些状态不对应真实支付机构、真实账户余额或真实退款。

### 11.4 Redis 和 RocketMQ 边界

Redis 用于 accessToken 黑名单、防重复提交和短时锁。核心状态仍以 MySQL 事务和状态校验为准。

RocketMQ 用于超时检查消息等异步触发。消费者必须重新读取 MySQL，并以 MySQL 状态条件更新决定是否关闭拼单。消息重复消费只能导致一次状态变更成功。

## 13. 老师可能提问与参考回答

**1. 这个系统和外卖平台有什么区别？**  
本系统只解决校园内部拼单协同，不接商家库存、骑手配送、真实支付和真实订单系统。商家名称、餐品和取餐点由学生填写。

**2. 为什么不接真实支付？**  
课程项目不处理真实资金更安全，也更符合系统定位。我们把支付抽象为模拟状态流，重点验证协同流程、状态机和数据一致性。

**3. 满减优惠如何分摊？**  
锁单后按成员原始金额比例分摊优惠，金额使用 BigDecimal 计算，尾差按固定规则处理，保证总额一致。

**4. 如何防止状态乱跳？**  
所有状态流转都由后端校验，终态禁止继续操作。前端按钮只是展示，不能代替后端权限和状态校验。

**5. Redis 是否是必须的？**  
认证黑名单使用 Redis；业务并发方面 Redis 只做防重复提交和短时锁，最终正确性仍依赖 MySQL 事务、状态条件更新和唯一约束。

**6. RocketMQ 在项目中做什么？**  
RocketMQ 用于超时检查等异步触发，不作为最终状态源。消费者收到消息后必须重新读取 MySQL 并幂等处理。

**7. LLM 在项目中发挥了什么作用？**  
LLM 辅助需求梳理、文档生成、代码骨架、测试用例和冲突分析。人工负责关键边界判断和验收，比如不做真实支付、控制状态数量、统一接口契约。

**8. 目前还有哪些不足？**  
需要补充最终部署截图、真实 RocketMQ 链路日志、浏览器截图验收；前端可继续做移动端细节优化和构建分包优化。
