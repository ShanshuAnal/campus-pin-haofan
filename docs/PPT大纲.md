## 老师可能提问与参考回答

### 1. 为什么不做真实支付？

本项目定位是校园拼单协同，不是交易平台。真实支付涉及资质、安全、对账、退款和合规问题，课程项目中用模拟支付状态流表达协作即可。

### 2. 模拟托管是不是平台真的收钱？

不是。`ESCROWED` 只是状态，表示参与者已经完成模拟支付动作，平台没有真实资金账户。

### 3. 金额分摊如何保证准确？

后端使用 `BigDecimal` 计算，锁单时统一计算原始总额、优惠分摊和应付总额，尾差按固定规则处理，避免前端自行计算。

### 4. Redis 和 RocketMQ 是不是过度设计？

Redis 用于 token 黑名单、防重复提交和短时锁；RocketMQ 用于超时检查等异步触发。核心状态仍由 MySQL 事务和状态校验保证，不把中间件作为最终状态源。

### 5. 如果 RocketMQ 消息重复消费怎么办？

消费者重新读取 MySQL，基于当前状态做条件更新。只有 `CREATED` 且超时的拼单能进入 `EXPIRED`，重复消息不会重复改变状态。

### 6. LLM 生成的代码如何保证可靠？

通过 AGENTS.md 限定技术栈、目录边界和交接格式；通过主控会话收口接口和数据库契约；通过测试会话补充单元测试、集成测试和回归验证。

### 7. 目前还有什么不足？

需要补充最终 ECS 截图、真实 RocketMQ 消费日志、浏览器截图验收；前端还可以继续做移动端细节和构建分包优化。

## 讲稿提示

- 不要把系统说成“外卖平台”。
- 不要说“已接入真实支付”。
- 模拟支付只讲状态流转。
- RocketMQ 只讲超时检查和异步增强，不讲分布式事务。
- 汇报测试结果时，以最终现场重新运行的截图为准。
