# 校园拼好饭系统 V2 升级设计说明

## 1. 升级背景

当前系统已经具备校园拼单 MVP 主流程，但整体仍偏基础：

- 业务闭环停留在创建、加入、锁定、付款和取餐；
- 文档经过多次补充后存在补丁化倾向；
- 前端交互更接近管理后台，缺少校园拼单产品体验；
- 取消、超时、延迟、异常和并发等真实协作场景尚未统一设计；
- Redis 和 RocketMQ 的增强边界需要重新明确。

V2 目标是在不推翻 MVP 的前提下，把系统升级为更完整的校园拼单协同产品。

## 2. V2 项目定位

校园拼好饭系统 V2 是面向高校学生的拼单协同产品，围绕“找拼单、凑满减、分摊优惠、标记付款、协同取餐、处理异常”形成完整闭环。

系统仍不是外卖平台：

- 不接入真实商家接口；
- 不接入真实支付；
- 不处理真实资金；
- 不做即时聊天；
- 不做复杂配送调度；
- 不做商家运营后台。

## 3. MVP 保留能力

V2 必须保留并兼容以下 MVP 能力：

- 轻量真实登录；
- accessToken + refreshToken；
- 发起拼单，支持同时填写发起人点餐内容；
- 加入拼单；
- 凑单金额计算；
- 锁定拼单；
- 优惠分摊；
- 模拟支付、模拟托管和付款状态展示；
- 指定取餐人；
- 推进取餐状态；
- 完成拼单；
- 我的拼单和数据看板。

## 4. V2 新增能力

### 4.0 开发准入审查结论

结论：V2 全局设计可以进入开发阶段，但必须按“核心闭环优先、增强能力后置”的方式推进。

审查判断：

- V2 没有扩展成外卖平台、支付系统、即时聊天或复杂运营后台，整体未明显过度设计。
- 取消拼单、超时关闭、延迟/异常事件和前端产品化改版直接补齐校园拼单真实协作缺口，属于 V2 必做。
- Redis 和 RocketMQ 的设计边界需要继续收紧：它们可以提高体验和可靠性，但不能成为拼单状态、金额计算或主流程完成的唯一依赖。
- V2 开发前需要先由 SQL 会话落地数据库结构，否则后端取消、超时和事件接口缺少字段和表支撑。
- V2 开发过程中不得引入真实支付、真实资金处理、商家接口、即时聊天、微服务拆分、分布式事务或复杂 RBAC。

### 4.1 V2 必做

- 取消拼单；
- 拼单超时自动关闭；
- 引入 `EXPIRED` 终态；
- 订单延迟和异常事件记录；
- MySQL 事务、状态校验、唯一约束和必要版本字段为主的并发控制；
- 拼单大厅产品化改版；
- 拼单详情页产品化改版；
- API、数据库、领域和测试文档统一。

### 4.2 V2 可选增强

- Redis 防重复提交；
- Redis 拼单短时锁；
- Redis 热点大厅和详情缓存；
- RocketMQ 异步通知；
- RocketMQ 超时检查；
- RocketMQ 统计聚合；
- 个人中心；
- 轻量级站内通知；
- 消息投递和消费记录表；
- 更细的退款、争议和履约复盘能力。

V2 必做和可选增强的分界：

| 能力 | V2 定位 | 开发边界 |
| --- | --- | --- |
| 取消拼单 | 必做 | 发起人操作，状态进入 `CANCELLED`，必须记录原因和事件 |
| 超时关闭 | 必做 | `CREATED` 超过截止时间进入 `EXPIRED`；状态更新以 MySQL 为准 |
| 延迟/异常事件 | 必做 | 新增事件记录与查询，不新增主状态 |
| MySQL 并发控制 | 必做 | 状态条件更新、事务、唯一约束、必要版本字段 |
| 前端产品化 | 必做 | 大厅和详情页从后台表格改为学生拼单产品体验 |
| Redis 防重复提交 | 可选增强 | 降低重复请求，不替代数据库约束 |
| Redis 短时锁 | 可选增强 | 辅助锁单等高冲突操作，不作为正确性唯一来源 |
| Redis 热点缓存 | 可选增强 | 优化大厅和详情读取，可失效、可重建 |
| RocketMQ 超时检查 | 可选增强实现路径 | 可以触发超时检查，但最终状态由 MySQL 服务层判定 |
| RocketMQ 通知/统计 | 可选增强 | 通知或统计失败不影响拼单主流程 |
| 个人中心 | V2 增量 | 只处理当前用户资料和密码，不扩展实名认证、头像上传或复杂账号体系 |
| 轻量通知 | V2 增量 | 接口查询通知，不做 WebSocket；通知失败不影响拼单主流程 |

## 5. 状态模型升级

### 5.1 拼单主状态

V2 拼单主状态：

```text
CREATED
LOCKED
ORDERED
DELIVERING
ARRIVED
PICKED_UP
FINISHED
CANCELLED
EXPIRED
```

设计原则：

- 主状态只表达拼单生命周期主线；
- `FINISHED`、`CANCELLED`、`EXPIRED` 是终态；
- `CANCELLED` 表示发起人主动取消；
- `EXPIRED` 表示系统因超时自动关闭；
- 延迟、缺餐、联系失败、付款争议等不新增主状态。

### 5.2 异常事件模型

V2 新增 `GroupOrderEvent` 概念，用于记录：

- 取消；
- 超时；
- 延迟；
- 取餐异常；
- 餐品缺失；
- 联系失败；
- 付款争议；
- 普通备注。

事件只追加，不覆盖历史。事件可以解释状态变化，但不替代状态。

## 6. 权限升级

| 能力 | 操作人 | 说明 |
| --- | --- | --- |
| 取消拼单 | 发起人 | 仅 `CREATED`、`LOCKED`、`ORDERED` 可取消 |
| 超时关闭 | 系统 | 仅 `CREATED` 且超过截止时间可过期 |
| 模拟支付 | 参与成员 | 只能操作自己的付款状态，成功后进入 `ESCROWED` |
| 确认模拟托管 | 发起人 | 只确认托管记录可见，不代表真实收款，不推进 `SETTLED` |
| 模拟结算 | 系统 | 拼单完成后将 `ESCROWED` 记录结算为 `SETTLED`，接收人为发起人 |
| 模拟退款 | 系统 | 拼单取消、超时关闭或异常终止时将 `ESCROWED` 记录推进为 `REFUNDED` |
| 指定取餐人 | 发起人 | 取餐人应为拼单成员或发起人 |
| 推进取餐 | 发起人或取餐人 | 必须按取餐状态顺序推进 |
| 记录延迟/异常 | 发起人或取餐人 | 普通成员权限后续可按事件类型开放 |

### 6.1 模拟支付与模拟托管资金流

V2 将“付款”明确限定为课程项目中的模拟资金状态流：

- 系统不接入真实支付渠道，不处理真实资金，不提供真实清算、提现、退款或对账能力；
- 参与者提交模拟支付后，资金状态从 `UNPAID` 变为 `ESCROWED`，表示平台模拟托管；
- 发起人是默认外部下单人，也是拼单完成后的模拟结算接收人；
- 取餐状态推进到 `DISTRIBUTED` 后，拼单主状态同步为 `FINISHED`，系统将 `ESCROWED` 记录模拟结算为 `SETTLED`；
- 拼单进入 `CANCELLED`、`EXPIRED` 或后续明确的异常终止场景时，尚未结算的 `ESCROWED` 记录进入 `REFUNDED`；
- `PAID`、`CONFIRMED` 不再作为 V2 资金流主状态，旧实现需要由后端会话迁移或兼容；
- 当前 `order_participant.payment_status` 和 `payment_record.payment_status` 均为 `varchar(32)`，可以表达 `ESCROWED`、`SETTLED`、`REFUNDED`，本次设计不要求修改数据库结构；
- 付款争议、异常退款说明等不新增主状态，统一通过 `group_order_event` 记录。

### 6.2 可见性规则

V2 需要区分“可在大厅看到”“可进入详情”“可查看事件时间线”三类权限。

| 页面/能力 | 可见性规则 | 说明 |
| --- | --- | --- |
| 拼单大厅 | 只展示公开可加入拼单和当前用户相关拼单 | 公开可加入拼单通常为 `CREATED` 且未截止；相关拼单包括我发起、我参与、我取餐 |
| `CREATED` 拼单详情 | 登录用户可查看公开详情并加入 | 未参与用户可以查看基本信息、成员人数、金额进度、取餐点和加入入口 |
| `LOCKED` 及之后详情 | 仅发起人、参与者、取餐人可查看 | 无关用户不能继续围观锁单后金额、付款、取餐和事件信息 |
| 事件时间线 | 仅发起人、参与者、取餐人可见 | 延迟、缺餐、联系失败、付款争议等事件属于拼单内部协同信息 |

前端必须使用详情接口返回的 `permissions` 控制操作和二次请求：

- `permissions.canJoin` 控制是否展示加入主按钮；
- `permissions.canCancel` 控制是否展示取消入口；
- `permissions.canCreateEvent` 控制是否展示新增事件入口；
- `permissions.canViewEvents` 控制是否请求和展示完整事件时间线；
- `canViewEvents=false` 时不得调用事件查询接口。

错误展示规则：

- 前端不得直接展示 raw 后端错误；
- `403` 应展示“你无权查看该拼单”或等价友好文案；
- `404` 应展示“拼单不存在或已不可访问”；
- `409` 应展示“拼单状态已变化，请刷新后重试”或具体业务文案；
- 不展示 Java 异常类名、SQL 错误、堆栈信息或未处理英文异常。

### 6.3 个人中心与轻量通知

个人中心用于补齐学生端产品体验，不扩展成复杂账号中心。

个人中心边界：

- 支持查看当前用户资料；
- 支持修改昵称、手机号、头像 URL、常用取餐点；
- 支持修改密码；
- 不做短信验证码；
- 不做实名认证；
- 不做头像文件上传；
- 不允许修改登录账号 `username`；
- 不影响发起拼单、加入拼单、模拟支付和取餐主流程。

轻量通知边界：

- 支持通知列表、未读数量、标记单条已读、全部已读；
- 通知来源包括有人加入拼单、拼单锁定、模拟支付、确认收款、取消拼单、超时关闭、异常事件；
- 通知通过接口查询，不做 WebSocket；
- 通知可同步写入，也可通过 RocketMQ 异步生成；
- 通知失败不得回滚拼单、付款、取餐或事件状态；
- RocketMQ 只是异步化增强，不是通知或主状态的唯一来源。

数据库边界：

- 当前 `user` 表已有 `nickname`、`phone`、`password_hash`、`password_update_time`，可支持昵称、手机号和密码修改；
- 当前 `user` 表缺少 `avatar_url` 与 `common_pickup_location`，需要 SQL 会话新增字段并同步后端实体和前端类型；
- 当前 `notification_record` 表已有 `receiver_id`、`biz_type`、`biz_id`、`title`、`content`、`status`、`read_time`，已能支撑轻量通知主需求；
- 暂不新增通知深链、站外推送、订阅偏好和通知删除能力。

## 7. 并发控制升级

V2 并发控制优先级：

1. MySQL 事务；
2. 状态条件更新；
3. 唯一约束；
4. 行级锁或乐观锁版本字段；
5. Redis 防重复提交和短时锁。

必须重点处理：

- 加入与锁定冲突；
- 加入与取消冲突；
- 锁定与超时冲突；
- 取消与超时冲突；
- 重复付款；
- 取餐状态重复推进；
- MQ 重复消费。

Redis 只能降低重复提交和热点冲突，不能替代 MySQL 正确性。

## 8. RocketMQ 边界

RocketMQ 可以用于：

- 超时检查；
- 异步通知；
- 统计聚合；
- 延迟提醒。

RocketMQ 不允许用于：

- 作为拼单状态源；
- 替代数据库事务；
- 直接决定最终金额；
- 作为唯一事件存储。

消费者必须重新读取 MySQL，并基于当前状态幂等处理。

超时关闭的最低实现要求：

- 必须提供后端服务层的超时关闭能力；
- 触发方式可以先使用定时任务或内部检查接口；
- RocketMQ 延迟消息是增强触发方式，不应阻塞 `EXPIRED` 状态落地；
- RocketMQ 重复消费时只能有一次状态更新成功。

## 9. 数据库变化建议

V2 建议由 SQL 会话后续落地：

- `group_order` 增加取消字段：`cancel_user_id`、`cancel_reason`、`cancel_time`；
- `group_order` 增加过期字段：`expired_time`、`expire_reason`；
- `group_order` 增加并发字段：`version`；
- `group_order` 增加列表体验字段：`last_event_time`；
- `group_order.status` 增加 `EXPIRED`；
- 新增 `group_order_event` 表；
- `user` 增加个人中心字段：`avatar_url`、`common_pickup_location`；
- 必要时新增 `async_message_record` 表；
- 为大厅查询、超时扫描、我的拼单和事件查询补充索引。

本次 V2 设计任务不修改 `sql/schema.sql` 和 `sql/data.sql`。

数据库开发准入要求：

| 变更点 | 是否必做 | 说明 |
| --- | --- | --- |
| `group_order.cancel_user_id` | 是 | 记录取消操作人 |
| `group_order.cancel_reason` | 是 | 记录发起人取消原因 |
| `group_order.cancel_time` | 是 | 记录取消时间 |
| `group_order.expired_time` | 是 | 记录系统超时关闭时间 |
| `group_order.expire_reason` | 是 | 记录超时关闭原因或系统说明 |
| `group_order.version` | 是 | 支撑关键状态并发控制 |
| `group_order.last_event_time` | 可选 | 优化列表事件展示和排序 |
| `group_order.status = EXPIRED` | 是 | 区分系统超时关闭和人工取消 |
| `group_order_event` | 是 | 支撑取消、超时、延迟、异常事件记录 |
| `user.avatar_url` | 是 | 支撑个人中心头像 URL，不处理文件上传 |
| `user.common_pickup_location` | 是 | 支撑个人中心常用取餐点 |
| `notification_record` 结构调整 | 否 | 现有字段已支撑轻量通知列表、未读数和已读流转 |
| `async_message_record` | 可选 | 仅在 RocketMQ 消费追踪需要时新增 |
| 大厅/超时/事件索引 | 是 | 支撑 V2 查询和超时扫描性能 |

## 10. API 变化建议

V2 新增或强化接口：

- `POST /api/group-orders/{id}/cancel`：取消拼单；
- 内部超时检查能力：用于系统触发 `EXPIRED`；
- `POST /api/group-orders/{id}/events`：新增履约事件；
- `GET /api/group-orders/{id}/events`：查询履约事件；
- `POST /api/group-orders/{id}/payments`：提交模拟支付，成功后进入 `ESCROWED`；
- `POST /api/group-orders/{id}/payments/{participantId}/confirm`：确认模拟托管记录，不触发真实收款，也不推进 `SETTLED`；
- `POST /api/internal/group-orders/{id}/payments/settle`：系统内部模拟结算，`FINISHED` 后将 `ESCROWED` 推进为 `SETTLED`；
- `POST /api/internal/group-orders/{id}/payments/refund`：系统内部模拟退款，取消、超时或异常终止后将 `ESCROWED` 推进为 `REFUNDED`；
- `POST /api/group-orders`：支持 `creatorItems`，发起拼单时可同步创建发起人参与记录和餐品明细；
- `GET /api/profile`：获取当前用户资料；
- `PUT /api/profile`：修改昵称、手机号、头像 URL 和常用取餐点；
- `PUT /api/profile/password`：修改密码；
- `GET /api/notifications`：查询通知列表；
- `GET /api/notifications/unread-count`：查询未读数量；
- `PATCH /api/notifications/{id}/read`：标记单条已读；
- `PATCH /api/notifications/read-all`：全部标记已读；
- `GET /api/group-orders`：增强大厅字段，支持产品化卡片；
- `GET /api/group-orders/{id}`：增强权限、成员、金额和事件字段；
- 写接口支持 `Idempotency-Key`；
- 取餐完成继续通过 `POST /api/group-orders/{id}/pickup-status` 推进到 `DISTRIBUTED`。

拼单接口路径统一使用 `/api/group-orders`。

API 开发准入要求：

| 接口或字段 | 是否必做 | 说明 |
| --- | --- | --- |
| `POST /api/group-orders/{id}/cancel` | 是 | 发起人取消拼单 |
| `POST /api/group-orders` 支持 `creatorItems` | 是 | 发起拼单时可同步填写发起人餐品 |
| 超时关闭服务或内部检查能力 | 是 | 不暴露给普通前端，供定时任务或 MQ 消费触发 |
| `POST /api/group-orders/{id}/events` | 是 | 新增延迟/异常/备注事件 |
| `GET /api/group-orders/{id}/events` | 是 | 查询事件时间线 |
| 详情响应 `permissions` | 是 | 前端按权限展示操作 |
| 详情响应 `permissions.canViewEvents` | 是 | 前端据此决定是否请求事件接口 |
| 详情响应 `recentEvents` | 是 | 支撑详情页事件区 |
| 大厅响应 `joinable`、`remainingSeconds`、`progressPercent` | 是 | 支撑产品化大厅卡片 |
| `/api/profile/**` | V2 增量 | 个人资料与密码管理，不允许修改 `username` |
| `/api/notifications/**` | V2 增量 | 接口查询通知，不做 WebSocket，不阻塞拼单主流程 |
| 写接口 `Idempotency-Key` | 可选 | Redis 防重复提交增强 |

接口开发注意事项：

- 取消后禁止加入、锁单、付款和取餐推进。
- 超时后禁止加入、锁单、付款和取餐推进。
- 模拟支付成功后进入 `ESCROWED`，拼单完成后由系统模拟结算为 `SETTLED`，取消、超时或异常终止后由系统模拟退款为 `REFUNDED`。
- 延迟事件不改变拼单主状态。
- 完成拼单继续通过 `POST /api/group-orders/{id}/pickup-status` 推进到 `DISTRIBUTED`。
- API 字段仍统一使用 `username`，不要回退到 `account`。

## 11. 前端产品化改版方向

### 11.1 拼单大厅

拼单大厅应作为产品首页，而不是后台列表。

重点能力：

- 可加入拼单优先展示；
- 店铺、取餐点、截止倒计时、凑单进度、成员数清晰可见；
- 支持关键词、取餐点和可加入筛选；
- 卡片式布局适配移动端；
- 状态标签和剩余时间应突出协作紧迫感。

实现安排：

1. 先对齐 `docs/04-API接口文档.md` 中的大厅字段，整理前端类型和状态映射。
2. 将大厅主视图从表格改为拼单卡片流。
3. 卡片必须展示店铺、取餐点、截止倒计时、凑单进度、参与人数、是否可加入。
4. `joinable = false` 时不展示加入主按钮。
5. `CREATED` 但已过截止时间的拼单应展示“已截止待处理”，不能允许继续加入。
6. 移动端优先保证卡片信息可读和主操作可触达。

### 11.1.1 发起拼单交互

V2 优化发起拼单后的体验：发起人不应被迫先创建拼单，再手动加入自己的拼单。

规则：

- 发起拼单表单默认展示“我的点餐”区域；
- 发起人可在创建拼单时同时填写自己的餐品；
- 前端通过 `creatorItems` 提交发起人的点餐内容；
- 若 `creatorItems` 非空，后端创建拼单后自动生成发起人的参与记录和餐品明细；
- 若 `creatorItems` 为空，仍允许创建空拼单，用于先建群再等成员加入的场景；
- 自动加入后，发起人不能再次加入自己的拼单；
- 创建成功后前端直接跳转拼单详情页。

金额汇总规则：

- 自动加入后需要更新 `participant_count`；
- 自动加入后需要更新 `original_total_amount`；
- 自动加入后需要更新 `payable_total_amount`；
- 未锁单前优惠尚未固化，`payable_total_amount` 默认等于 `original_total_amount`；
- 锁单后再按原有优惠分摊规则计算实际应付金额。

数据库边界：

- 不新增表，不新增字段；
- 复用 `order_participant` 保存发起人参与记录；
- 复用 `meal_item` 保存发起人餐品明细；
- 后端必须用事务保证拼单、参与记录、餐品明细和金额汇总一致。

### 11.2 拼单详情页

详情页应围绕一次拼单协同组织：

- 顶部展示当前状态、倒计时、取餐点和主操作；
- 明确展示当前用户可执行操作；
- 成员点单和金额分摊清晰呈现；
- 付款状态、取餐状态和事件时间线分区；
- 取消、延迟、异常等操作按权限展示。

实现安排：

1. 顶部固定呈现拼单主状态、取餐点、截止时间、主操作按钮。
2. 主操作按钮必须以后端 `permissions` 字段为准。
3. 成员区展示餐品、原始金额、分摊优惠、应付金额、付款状态。
4. 取餐区展示取餐人、取餐状态和下一步可执行动作。
5. 事件区展示 `recentEvents`，完整时间线通过事件查询接口加载。
6. `CANCELLED`、`EXPIRED`、`FINISHED` 终态下隐藏加入、锁单、付款和取餐推进主操作。
7. `permissions.canViewEvents=false` 时不请求事件接口，也不渲染完整事件时间线入口。

### 11.3 我的拼单

我的拼单应按任务视角组织：

- 我发起的；
- 我参与的；
- 我负责取餐的；
- 待付款；
- 历史拼单。

### 11.4 取消、超时和异常提示

前端需要对 V2 新状态和事件给出清晰提示：

- 取消成功后详情页进入 `CANCELLED` 终态，展示取消原因和取消时间；
- `LOCKED` 且已有成员付款时，取消失败应提示“已有付款记录，需线下协商或记录异常”；
- `EXPIRED` 表示系统超时关闭，不展示取消原因；
- 延迟和异常不改变主状态，展示在事件时间线；
- 事件提交成功后刷新详情页 `recentEvents` 和事件列表；
- 前端不能用事件类型替代主状态判断。
- 前端需要统一封装错误提示，不得直接展示 raw 后端错误内容。

### 11.5 个人中心与通知入口

个人中心前端重点：

- 顶部用户菜单进入个人中心；
- 资料页展示账号、昵称、手机号、头像 URL、常用取餐点；
- 昵称、手机号、头像 URL、常用取餐点可编辑；
- 修改密码独立成表单，成功后引导重新登录；
- 不展示实名认证、短信验证、头像上传等未实现入口。

通知前端重点：

- 顶部展示未读数量；
- 通知列表按时间倒序展示；
- 通知点击后可跳转到相关拼单详情；
- 支持单条已读和全部已读；
- 通知错误不得影响大厅、详情和主流程操作。

## 15. 最终准入结论

V2 可以进入开发阶段，推荐从 `V2-T002` 开始推进。

推进原则：

1. 先落地 SQL，再开发后端核心接口。
2. 后端先做取消、超时、事件，再做 Redis 和 RocketMQ 增强。
3. 前端先重构大厅，再重构详情页，最后联调取消、超时和异常提示。
4. 测试在后端核心能力完成后尽早介入，不等全部前端完成。
5. Redis 和 RocketMQ 增强不能阻塞取消、超时和事件主闭环。
