# 校园拼好饭系统 V2 升级设计说明

## 1. 升级背景

当前系统已经具备校园拼单 MVP 主流程，但整体仍偏基础：

- 业务闭环停留在创建、加入、锁定、付款和取餐；
- 文档经过多次补充后存在补丁化倾向；
- 前端交互更接近管理后台，缺少校园拼单产品体验；
- 取消、超时、延迟、异常和并发等真实协作场景尚未统一设计；
- Redis 和 RocketMQ 的增强边界需要重新明确。

V2 目标是在不推翻 MVP 的前提下，把系统升级为更完整的校园拼单协同产品。

## 2. V2 项目定位

校园拼好饭系统 V2 是面向高校学生的拼单协同产品，围绕“找拼单、凑满减、分摊优惠、标记付款、协同取餐、处理异常”形成完整闭环。

系统仍不是外卖平台：

- 不接入真实商家接口；
- 不接入真实支付；
- 不做即时聊天；
- 不做复杂配送调度；
- 不做商家运营后台。

## 3. MVP 保留能力

V2 必须保留并兼容以下 MVP 能力：

- 轻量真实登录；
- accessToken + refreshToken；
- 发起拼单；
- 加入拼单；
- 凑单金额计算；
- 锁定拼单；
- 优惠分摊；
- 标记付款和确认付款；
- 指定取餐人；
- 推进取餐状态；
- 完成拼单；
- 我的拼单和数据看板。

## 4. V2 新增能力

### 4.1 V2 必做

- 取消拼单；
- 拼单超时自动关闭；
- 引入 `EXPIRED` 终态；
- 订单延迟和异常事件记录；
- MySQL 事务、状态校验、唯一约束和版本字段为主的并发控制；
- 拼单大厅产品化改版；
- 拼单详情页产品化改版；
- API、数据库、领域和测试文档统一。

### 4.2 V2 可选增强

- Redis 防重复提交；
- Redis 拼单短时锁；
- Redis 热点大厅和详情缓存；
- RocketMQ 异步通知；
- RocketMQ 超时检查；
- RocketMQ 统计聚合；
- 消息投递和消费记录表；
- 更细的退款、争议和履约复盘能力。

## 5. 状态模型升级

### 5.1 拼单主状态

V2 拼单主状态：

```text
CREATED
LOCKED
ORDERED
DELIVERING
ARRIVED
PICKED_UP
FINISHED
CANCELLED
EXPIRED
```

设计原则：

- 主状态只表达拼单生命周期主线；
- `FINISHED`、`CANCELLED`、`EXPIRED` 是终态；
- `CANCELLED` 表示发起人主动取消；
- `EXPIRED` 表示系统因超时自动关闭；
- 延迟、缺餐、联系失败、付款争议等不新增主状态。

### 5.2 异常事件模型

V2 新增 `GroupOrderEvent` 概念，用于记录：

- 取消；
- 超时；
- 延迟；
- 取餐异常；
- 餐品缺失；
- 联系失败；
- 付款争议；
- 普通备注。

事件只追加，不覆盖历史。事件可以解释状态变化，但不替代状态。

## 6. 权限升级

| 能力 | 操作人 | 说明 |
| --- | --- | --- |
| 取消拼单 | 发起人 | 仅 `CREATED`、`LOCKED`、`ORDERED` 可取消 |
| 超时关闭 | 系统 | 仅 `CREATED` 且超过截止时间可过期 |
| 标记付款 | 参与成员 | 只能操作自己的付款状态 |
| 确认付款 | 发起人 | 确认成员线下付款 |
| 指定取餐人 | 发起人 | 取餐人应为拼单成员或发起人 |
| 推进取餐 | 发起人或取餐人 | 必须按取餐状态顺序推进 |
| 记录延迟/异常 | 发起人或取餐人 | 普通成员权限后续可按事件类型开放 |

## 7. 并发控制升级

V2 并发控制优先级：

1. MySQL 事务；
2. 状态条件更新；
3. 唯一约束；
4. 行级锁或乐观锁版本字段；
5. Redis 防重复提交和短时锁。

必须重点处理：

- 加入与锁定冲突；
- 加入与取消冲突；
- 锁定与超时冲突；
- 取消与超时冲突；
- 重复付款；
- 取餐状态重复推进；
- MQ 重复消费。

Redis 只能降低重复提交和热点冲突，不能替代 MySQL 正确性。

## 8. RocketMQ 边界

RocketMQ 可以用于：

- 超时检查；
- 异步通知；
- 统计聚合；
- 延迟提醒。

RocketMQ 不允许用于：

- 作为拼单状态源；
- 替代数据库事务；
- 直接决定最终金额；
- 作为唯一事件存储。

消费者必须重新读取 MySQL，并基于当前状态幂等处理。

## 9. 数据库变化建议

V2 建议由 SQL 会话后续落地：

- `group_order` 增加取消字段：`cancel_user_id`、`cancel_reason`、`cancel_time`；
- `group_order` 增加过期字段：`expired_time`、`expire_reason`；
- `group_order` 增加并发字段：`version`；
- `group_order` 增加列表体验字段：`last_event_time`；
- `group_order.status` 增加 `EXPIRED`；
- 新增 `group_order_event` 表；
- 必要时新增 `async_message_record` 表；
- 为大厅查询、超时扫描、我的拼单和事件查询补充索引。

本次 V2 设计任务不修改 `sql/schema.sql` 和 `sql/data.sql`。

## 10. API 变化建议

V2 新增或强化接口：

- `POST /api/group-orders/{id}/cancel`：取消拼单；
- 内部超时检查能力：用于系统触发 `EXPIRED`；
- `POST /api/group-orders/{id}/events`：新增履约事件；
- `GET /api/group-orders/{id}/events`：查询履约事件；
- `GET /api/group-orders`：增强大厅字段，支持产品化卡片；
- `GET /api/group-orders/{id}`：增强权限、成员、金额和事件字段；
- 写接口支持 `Idempotency-Key`；
- 取餐完成继续通过 `POST /api/group-orders/{id}/pickup-status` 推进到 `DISTRIBUTED`。

拼单接口路径统一使用 `/api/group-orders`。

## 11. 前端产品化改版方向

### 11.1 拼单大厅

拼单大厅应作为产品首页，而不是后台列表。

重点能力：

- 可加入拼单优先展示；
- 店铺、取餐点、截止倒计时、凑单进度、成员数清晰可见；
- 支持关键词、取餐点和可加入筛选；
- 卡片式布局适配移动端；
- 状态标签和剩余时间应突出协作紧迫感。

### 11.2 拼单详情页

详情页应围绕一次拼单协同组织：

- 顶部展示当前状态、倒计时、取餐点和主操作；
- 明确展示当前用户可执行操作；
- 成员点单和金额分摊清晰呈现；
- 付款状态、取餐状态和事件时间线分区；
- 取消、延迟、异常等操作按权限展示。

### 11.3 我的拼单

我的拼单应按任务视角组织：

- 我发起的；
- 我参与的；
- 我负责取餐的；
- 待付款；
- 历史拼单。
